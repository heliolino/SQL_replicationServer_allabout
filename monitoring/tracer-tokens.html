Tracer Tokens — latency, measured honestly

A tracer token is a tiny marker transaction written into the publisher's log. It rides the real pipeline like any other transaction, and the system records the timestamp at each hop — giving you exact publisher→distributor and distributor→subscriber latency, per subscription. Transactional replication only.

the tracer token riding the normal pipeline

Why the split matters more than the total

PatternDiagnosis
t₁−t₀ large, t₂−t₁ smallLog Reader leg is behind: agent stopped/failing, giant transaction being chewed, publisher log issues → start at Publisher
t₁−t₀ small, t₂−t₁ largeDelivery leg: Distribution Agent stopped, subscriber blocking/timeouts, network, one subscription only vs all → start at Subscriber
Both largeDistributor itself (IO pressure, cleanup blocking) or everything down → start at Distributor
Token never arrivesPipeline fully stopped for that subscription — check agent states before anything else

Using tokens from T-SQL

-- 1. post a token (at the publisher, in the publication DB)
USE SalesDB;
DECLARE @token_id int;
EXEC sp_posttracertoken
     @publication = N'SalesPub',
     @tracer_token_id = @token_id OUTPUT;
SELECT @token_id AS token_id;

-- 2. read results (wait a bit; at publisher or distributor)
EXEC sp_helptracertokenhistory
     @publication = N'SalesPub',
     @tracer_id = @token_id;
-- columns: distributor_latency (t1-t0), subscriber, subscriber_latency (t2-t1),
--          overall_latency — NULL until the token reaches that hop

-- list tokens posted in the last days
EXEC sp_helptracertokens @publication = N'SalesPub';

-- cleanup old token metadata (also removed by retention cleanup)
EXEC sp_deletetracertokenhistory @publication = N'SalesPub', @cutoff_date = '2026-11-01';

In Replication Monitor: publication → Tracer Tokens tab → Insert Tracer — same data, clickable.

Continuous latency monitoring with tokens

A common pattern: a SQL Agent job posts a token every 5–15 minutes and a second step (after a delay) checks the result, raising an error if latency exceeds the SLA — giving you the alerting Replication Monitor can't do:

DECLARE @token_id int, @latency int;
EXEC sp_posttracertoken @publication = N'SalesPub', @tracer_token_id = @token_id OUTPUT;
WAITFOR DELAY '00:02:00';   -- give it time to flow

SELECT @latency = MAX(DATEDIFF(SECOND, 0, ISNULL(overall_latency, '01:00:00')))
FROM (SELECT overall_latency = NULL) placeholder;  -- replace with sp_helptracertokenhistory INSERT…EXEC pattern

-- real implementations: INSERT the proc output into a temp table, then:
IF @latency IS NULL OR @latency > 300
    RAISERROR('Replication latency for SalesPub exceeds 300s (or token lost)', 16, 1) WITH LOG;
✅ Tokens are cheap

A token is a single tiny transaction — safe to post every few minutes even on busy systems. It measures the same path user transactions take, which makes it the most honest latency metric available; counters like sp_replcounters estimate, tokens measure.

Limitations

  • Transactional (and P2P) publications only — no merge, no snapshot.
  • A token measures the pipeline from now: posting one during an incident tells you about new work, while the backlog ahead of it still has to drain — pair tokens with the undistributed commands count for the full picture.
  • Requires agents actually running; a lost token is itself a finding.
