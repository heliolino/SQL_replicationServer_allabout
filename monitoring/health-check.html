The health check — every component alive, on time, and identical

One repeatable sweep that turns "is replication OK?" into a scripted health event: confirm each component is active and healthy, measure the latency of the pipeline, and verify the replicated tables actually hold the same number of rows. Everything here is copy-paste T-SQL you can run ad hoc or schedule as a logged check.

what "healthy" must mean at each component — each claim backed by a check on this page

Health is four questions, in order

#QuestionAnswered byFails as
1Alive? — are the agents and services running at all?Component liveness checksStopped job, failed login, dead SQL Agent
2Moving? — are the watermarks actually advancing?Is It Moving? (dedicated page)Agent "running" but frozen
3On time? — is end-to-end latency inside your SLA?Latency measurementBacklog, slow apply, blocked subscriber
4Identical? — do the replicated tables hold the same rows?Row-count & validation checksSilent divergence (the worst failure mode)

A system can pass 1 and fail 2 (running-but-stuck), pass 1–3 and fail 4 (someone skipped errors last month). Only all four together mean healthy.

Check 1 — component liveness: is every part active?

  1. Is SQL Server Agent itself running on each server? No Agent service → no replication agents, whatever the job history says. Run on publisher, distributor and subscriber (pull): 
    SELECT servicename, status_desc, last_startup_time
FROM sys.dm_server_services
WHERE servicename LIKE N'SQL Server Agent%';
-- status_desc must be 'Running'
  2. Are the replication jobs in the state they should be in? Continuous agents (Log Reader, Distribution in default profile, Queue Reader) should show RUNNING; Snapshot and the cleanup jobs run on schedule and should show a recent successful stop: 
    SELECT  j.name, category = c.name,
        state = CASE WHEN a.start_execution_date IS NOT NULL
                      AND a.stop_execution_date IS NULL
                     THEN 'RUNNING' ELSE 'stopped' END,
        a.start_execution_date, a.stop_execution_date
FROM msdb.dbo.sysjobs j
JOIN msdb.dbo.syscategories c ON c.category_id = j.category_id
LEFT JOIN msdb.dbo.sysjobactivity a ON a.job_id = j.job_id
  AND a.session_id = (SELECT MAX(session_id) FROM msdb.dbo.syssessions)
WHERE c.name LIKE 'REPL-%'
ORDER BY c.name, j.name;
  3. Health, not just liveness: the last session verdict per agent. A job can be RUNNING while the agent inside it is stuck in a retry loop. The history tables tell the truth — runstatus 5 (retrying) and 6 (failed) are your incidents, 3/4 (in progress / idle) are healthy: 
    USE distribution;
;WITH h AS (
  SELECT agent_type = 'Log Reader', agent = a.name, h.runstatus, h.start_time,
         h.comments,
         rn = ROW_NUMBER() OVER (PARTITION BY h.agent_id ORDER BY h.timestamp DESC)
  FROM dbo.MSlogreader_history h
  JOIN dbo.MSlogreader_agents a ON a.id = h.agent_id
  UNION ALL
  SELECT 'Distribution', a.name, h.runstatus, h.start_time, h.comments,
         ROW_NUMBER() OVER (PARTITION BY h.agent_id ORDER BY h.timestamp DESC)
  FROM dbo.MSdistribution_history h
  JOIN dbo.MSdistribution_agents a ON a.id = h.agent_id
  UNION ALL
  SELECT 'Snapshot', a.name, h.runstatus, h.start_time, h.comments,
         ROW_NUMBER() OVER (PARTITION BY h.agent_id ORDER BY h.timestamp DESC)
  FROM dbo.MSsnapshot_history h
  JOIN dbo.MSsnapshot_agents a ON a.id = h.agent_id
)
SELECT agent_type, agent, start_time,
       state = CASE runstatus WHEN 1 THEN 'Starting'    WHEN 2 THEN 'Succeeded'
                              WHEN 3 THEN 'In progress' WHEN 4 THEN 'Idle (healthy)'
                              WHEN 5 THEN 'RETRYING  <<< investigate'
                              WHEN 6 THEN 'FAILED    <<< incident' END,
       last_message = comments
FROM h
WHERE rn = 1
ORDER BY CASE runstatus WHEN 6 THEN 0 WHEN 5 THEN 1 ELSE 2 END, agent_type, agent;
  4. The official rollup — same codes, aggregated per publication/subscription (status 6 = failed, 5 = retrying, with latency columns included): 
    USE distribution;
EXEC sp_replmonitorhelppublication  @publisher = N'PUB01';
EXEC sp_replmonitorhelpsubscription @publisher = N'PUB01', @publication_type = 0;
    These read the cache table dbo.MSreplication_monitordata, refreshed by the Replication monitoring refresher for distribution job — if that job is stopped, the rollup silently goes stale (⚠ monitor blindness on the risk checklist).

Check 2 — one health-event snapshot (scriptable)

This single result set is the "health event": component / metric / value / verdict, from one connection to the distributor. Green across the board = questions 1 and most of 3 answered. 

USE distribution;
SET NOCOUNT ON;

SELECT  component = N'Distributor queue', item = N'commands waiting',
        value   = CONVERT(nvarchar(30), COUNT_BIG(*)),
        verdict = CASE WHEN COUNT_BIG(*) < 500000 THEN N'OK' ELSE N'WARN - backlog' END
FROM dbo.MSrepl_commands WITH (NOLOCK)

UNION ALL
SELECT  N'Distributor queue', N'newest queued txn age (min)',
        CONVERT(nvarchar(30), ISNULL(DATEDIFF(MINUTE, MAX(entry_time), GETDATE()), -1)),
        CASE WHEN MAX(entry_time) IS NULL THEN N'OK - empty'
             WHEN DATEDIFF(MINUTE, MAX(entry_time), GETDATE()) < 10 THEN N'OK - fresh arrivals'
             ELSE N'WARN - nothing arriving: Log Reader?' END
FROM dbo.MSrepl_transactions

UNION ALL
SELECT  N'Agents', N'errors in last 60 min',
        CONVERT(nvarchar(30), COUNT_BIG(*)),
        CASE WHEN COUNT_BIG(*) = 0 THEN N'OK' ELSE N'FAIL - read MSrepl_errors' END
FROM dbo.MSrepl_errors
WHERE time > DATEADD(MINUTE, -60, GETDATE())

UNION ALL
SELECT  N'Subscriptions', N'inactive (status = 0)',
        CONVERT(nvarchar(30), COUNT_BIG(*)),
        CASE WHEN COUNT_BIG(*) = 0 THEN N'OK'
             ELSE N'FAIL - needs reinitialization' END
FROM dbo.MSsubscriptions
WHERE status = 0 AND subscriber_db <> N'virtual'

UNION ALL
SELECT  N'Agents', N'sessions failed/retrying (last 2 h)',
        CONVERT(nvarchar(30), COUNT_BIG(*)),
        CASE WHEN COUNT_BIG(*) = 0 THEN N'OK' ELSE N'FAIL - see liveness check 3' END
FROM dbo.MSdistribution_history
WHERE runstatus IN (5, 6)
  AND start_time > DATEADD(HOUR, -2, GETDATE());

Complete the event with two publisher-side numbers — EXEC sp_replcounters; (pending transaction count + latency per published DB) and SELECT name, log_reuse_wait_desc FROM sys.databases WHERE is_published = 1; (anything stuck on REPLICATION = Log Reader falling behind, see the LSN deep dive).

Check 3 — measuring latency

  1. Tracer token — the exact, on-demand answer (transactional only). Posts a marker transaction and timestamps it at each hop; mechanics on the tracer tokens page. Fully scriptable as a probe: 
    USE SalesDB;
DECLARE @token int;
EXEC sp_posttracertoken @publication = N'SalesPub',
                        @tracer_token_id = @token OUTPUT;

WAITFOR DELAY '00:00:30';   -- give it time to ride the pipeline

EXEC sp_helptracertokenhistory @publication = N'SalesPub',
                               @tracer_id   = @token;
-- distributor_latency  = publisher -> distributor (Log Reader leg)
-- subscriber_latency   = distributor -> subscriber (Distribution Agent leg)
-- overall_latency      = end to end;  NULL = token has NOT arrived there yet
    A token that never completes is itself a finding — go to Is It Moving? to find which hop ate it.
  2. Continuous latency without injecting anything — the monitor rollup carries a live estimate per subscription: 
    USE distribution;
EXEC sp_replmonitorhelpsubscription @publisher = N'PUB01', @publication_type = 0;
-- 'latency' column (seconds, estimated); status 5/6 override any latency reading
    Publisher-to-distributor leg only: EXEC sp_replcounters; — the replication latency column, plus throughput in txn/s.
  3. Heartbeat table — latency as data, for any replication type. Replicate a one-row table that the publisher updates every minute; the subscriber's lag is then an ordinary query, perfect for dashboards and non-transactional topologies where tracer tokens don't exist. Full pattern on Is It Moving?; the measurement itself: 
    SELECT lag_seconds = DATEDIFF(SECOND, last_beat, SYSUTCDATETIME())
FROM dbo.ReplHeartbeat;   -- replicated article, publisher updates it each minute
  4. Trend it — Perfmon counters Logreader:Delivery Latency and Dist:Delivery Latency (see the query toolbox) separate "slow today" from "slow always".
MethodMeasuresPrecisionBest for
Tracer tokenBoth legs + total, per subscriptionExactOn-demand proof, SLA evidence
sp_replmonitorhelpsubscriptionPer-subscription estimateEstimatedDashboards, the health snapshot above
sp_replcountersPublisher → distributor leg onlyEstimatedIsolating the Log Reader leg

Check 4 — are the tables actually identical? Row counts & validation

⚠ A healthy pipeline makes counts differ — briefly

While transactions are in flight, publisher and subscriber counts legitimately disagree by the size of the backlog. Read a row-count difference together with queue depth (check 2): small diff + draining queue = healthy; any diff + empty queue and idle agents = real divergence. Row filters on articles also make counts differ by design — compare filtered articles with the filter applied.

  1. The official way — validation. Queues a row-count (or row-count + binary checksum) comparison that the Distribution Agent executes and reports in its history; failures raise the 20574-class alerts (wire them on the alerts page): 
    USE SalesDB;
-- whole publication
EXEC sp_publication_validation
     @publication   = N'SalesPub',
     @rowcount_only = 1,      -- 1 = row counts only (fast) | 2 = counts + checksum
     @full_or_fast  = 2;      -- fast counts from metadata where safe

-- or one article only
EXEC sp_article_validation
     @publication = N'SalesPub', @article = N'Orders',
     @rowcount_only = 2, @full_or_fast = 2;

-- results: Distribution Agent history (Replication Monitor or MSdistribution_history)
  2. The instant side-by-side — metadata counts over a linked server. No agent involvement, runs in seconds even on huge tables, compares only the published articles. Approximate under concurrent DML (reads allocation metadata, not the rows): 
    USE SalesDB;
;WITH pub AS (
  SELECT  obj = s.name + N'.' + t.name,
          pub_rows = SUM(ps.row_count)
  FROM sys.dm_db_partition_stats ps
  JOIN sys.tables   t ON t.object_id = ps.object_id
  JOIN sys.schemas  s ON s.schema_id = t.schema_id
  JOIN dbo.sysarticles a ON a.objid  = t.object_id     -- published articles only
  WHERE ps.index_id IN (0, 1)                          -- heap or clustered index = the rows
  GROUP BY s.name, t.name
),
sub AS (
  SELECT  obj = s.name + N'.' + t.name,
          sub_rows = SUM(ps.row_count)
  FROM SUB01.SalesReporting.sys.dm_db_partition_stats ps
  JOIN SUB01.SalesReporting.sys.tables  t ON t.object_id = ps.object_id
  JOIN SUB01.SalesReporting.sys.schemas s ON s.schema_id = t.schema_id
  WHERE ps.index_id IN (0, 1)
  GROUP BY s.name, t.name
)
SELECT  p.obj, p.pub_rows,
        sub_rows = ISNULL(b.sub_rows, 0),
        diff     = p.pub_rows - ISNULL(b.sub_rows, 0),
        verdict  = CASE WHEN b.sub_rows IS NULL       THEN N'FAIL - table missing at subscriber'
                        WHEN p.pub_rows = b.sub_rows  THEN N'OK'
                        ELSE N'CHECK - differs (backlog? filter? drift?)' END
FROM pub p
LEFT JOIN sub b ON b.obj = p.obj
ORDER BY ABS(p.pub_rows - ISNULL(b.sub_rows, 0)) DESC;
  3. No linked server? Generate exact COUNT scripts from the article list and run the output on both sides (exact, but scans; use off-peak for big tables): 
    USE SalesDB;
SELECT N'SELECT tbl = ''' + s.name + N'.' + t.name + N''', rows = COUNT_BIG(*) FROM '
       + QUOTENAME(s.name) + N'.' + QUOTENAME(t.name) + N' UNION ALL'
FROM dbo.sysarticles a
JOIN sys.tables  t ON t.object_id = a.objid
JOIN sys.schemas s ON s.schema_id = t.schema_id
ORDER BY s.name, t.name;
-- paste the output (drop the last UNION ALL), run at publisher AND subscriber, diff the two grids
  4. Counts match but you still doubt the content? Row counts can agree while values differ. Escalate to checksum validation (@rowcount_only = 2 above) or a row-level diff with repair script generation: 
    tablediff.exe -sourceserver PUB01 -sourcedatabase SalesDB -sourcetable Orders
              -destinationserver SUB01 -destinationdatabase SalesReporting
              -destinationtable Orders -f C:\Temp\fix_Orders.sql
🛑 Never "fix" a difference by making the check pass

A real divergence means rows were skipped, written locally, or a reinit went wrong. Repair the data (re-insert, tablediff -f, or reinitialize) and find the cause — usually a 20598/2627 history or a -SkipErrors someone left behind. Divergence found = start the triage workflow at the data-mismatch branch.

Put it on a schedule — the logged health event

Run the snapshot every 5 minutes from a SQL Agent job on the distributor, keep history, and raise an alertable error on any FAIL:

USE distribution;
-- one-time
CREATE TABLE dbo.ReplHealthLog (
  logged_at datetime2     NOT NULL DEFAULT SYSUTCDATETIME(),
  component nvarchar(60)  NOT NULL,
  item      nvarchar(100) NOT NULL,
  value     nvarchar(60)  NOT NULL,
  verdict   nvarchar(80)  NOT NULL
);

-- job step (every 5 min): insert the health snapshot from check 2
INSERT dbo.ReplHealthLog (component, item, value, verdict)
SELECT component, item, value, verdict
FROM ( /* paste the UNION ALL health snapshot query here */ ) AS snap;

-- then fire an alert if this run produced a failure
IF EXISTS (SELECT 1 FROM dbo.ReplHealthLog
           WHERE logged_at > DATEADD(MINUTE, -5, SYSUTCDATETIME())
             AND verdict LIKE N'FAIL%')
  RAISERROR('Replication health check FAILED - see distribution.dbo.ReplHealthLog', 16, 1) WITH LOG;
-- WITH LOG writes to the SQL error log -> catchable by a SQL Agent alert
-- wire the operator notification on the Alerts page

Hook the RAISERROR into an operator notification exactly as described on the alerts & thresholds page, and trend ReplHealthLog for capacity planning — queue depth and latency creeping up over weeks is the early warning no single snapshot shows.

✅ When a check fails

Any red verdict on this page has a guided follow-up: start the Incident Triage Workflow (step 2 of the troubleshooting path), use Is It Moving? for frozen-but-running agents, the LSN deep dive for a stuck position, and Common Errors once you have the error number.
