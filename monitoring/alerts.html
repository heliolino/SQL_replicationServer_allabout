Alerts & thresholds — being told before the users tell you

Out of the box, replication fails silently (risk ⚠ Monitoring gap). This page wires up the three layers that fix that: canned replication alerts, agent-state checks, and threshold warnings.

☁ On Azure SQL Managed Instance

MI runs a full SQL Server Agent, so everything on this page carries over: the canned replication alerts are created on the distributor MI, operators and job-failure notifications work, and the delivery channel is Database Mail — which on MI must first be enabled (sp_configure 'database mail xps', 1) and configured with an external SMTP relay such as SendGrid or your mail gateway. For the scheduled health event feeding these alerts, see the health check page.

Layer 1 — the canned replication alerts

Configuring a distributor pre-creates (disabled) SQL Agent alerts on the distributor. Enable the ones you need, attach operators/notifications, and they fire on the corresponding message IDs:

-- operator (once)
EXEC msdb.dbo.sp_add_operator @name = N'DBA-OnCall',
     @email_address = N'dba-oncall@example.com';

-- enable the canned alert and attach notification
EXEC msdb.dbo.sp_update_alert @name = N'Replication: agent failure', @enabled = 1;
EXEC msdb.dbo.sp_add_notification
     @alert_name = N'Replication: agent failure',
     @operator_name = N'DBA-OnCall', @notification_method = 1;  -- email

-- verify what exists
SELECT name, enabled, message_id FROM msdb.dbo.sysalerts WHERE name LIKE 'Replication%';

Database Mail must be configured and SQL Agent set to use it (Agent properties → Alert System) or nothing sends — the most common reason "alerts were on but nobody was told".

Layer 2 — agent state & latency check job

Alerts fire on failures. A stopped or silently idle agent never fails — cover it with a scheduled check job (every 5–10 min) feeding your monitoring platform: 

-- continuous REPL jobs that are NOT currently executing = incident
SELECT j.name
FROM msdb.dbo.sysjobs j
JOIN msdb.dbo.syscategories c ON c.category_id = j.category_id
WHERE c.name IN ('REPL-LogReader','REPL-Distribution')   -- continuous categories
  AND j.enabled = 1
  AND NOT EXISTS (SELECT 1 FROM msdb.dbo.sysjobactivity a
                  WHERE a.job_id = j.job_id
                    AND a.start_execution_date IS NOT NULL
                    AND a.stop_execution_date IS NULL);

-- subscriptions in failed/retrying state
USE distribution;
SELECT publication, subscriber_db = s.subscriber_db, s.status
FROM dbo.MSdistribution_agents a
JOIN dbo.MSsubscriptions sub ON sub.agent_id = a.id
JOIN dbo.MSpublications p    ON p.publication_id = sub.publication_id
CROSS APPLY (SELECT TOP 1 runstatus AS status, subscriber_db = a.subscriber_db
             FROM dbo.MSdistribution_history h
             WHERE h.agent_id = a.id ORDER BY h.timestamp DESC) s
WHERE s.status IN (5, 6);   -- 5 retry, 6 fail

Add the tracer-token latency job as the third check, and the "Replication agents checkup" job (created with the distributor) acts as a built-in heartbeat: it raises error 20554/20557 — alertable — when an agent stops logging progress.

Layer 3 — Replication Monitor threshold warnings

Set per subscription in Replication Monitor (Warnings tab); they change status to ⚠ and raise messages 20572/20573 which you can also alert on:

  • Latency (transactional): set to your SLA (e.g. 60 s), not the default 30 s if that just creates noise.
  • Expiration: warn at 70–80% of retention — leaves ~3 days of runway on default retention.
  • Merge: sync duration and rows/sec thresholds for slow-link detection.

✅ Test the whole chain once a quarter

Stop a Distribution Agent in a test window and confirm a human actually gets paged within the promised time. Alert chains rot: operators leave, Database Mail profiles break, thresholds drift. The quarterly fire-drill catches it.
