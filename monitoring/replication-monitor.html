Replication Monitor

The purpose-built GUI (sqlmonitor.exe, launched from SSMS → right-click Replication → Launch Replication Monitor). It reads the distribution database's history tables and presents per-publication health, latency, and agent sessions. Learn its layout before the incident, not during.

☁ Works against Azure SQL Managed Instance

Launch Replication Monitor from SSMS on your workstation and register the distributor MI by its FQDN with a SQL authentication login — the tool reads the same distribution-DB history tables described below, so everything on this page applies. The scripted equivalents (and the MI-friendly health check sweep) matter even more on MI, where you'll often be querying over a VPN rather than RDP'ing to a server.

The tabs that answer support questions

QuestionWhere
"Is anything broken right now?"Root node → All Subscriptions: red ❌ = erroring, amber ⚠ = threshold exceeded
"How far behind are we?"Publication → All Subscriptions → Latency column; precise numbers via Tracer Tokens tab
"How much is queued?"Subscription detail → Undistributed Commands: count + estimated apply time
"What exactly failed?"Double-click subscription → Distributor To Subscriber History → error detail in the session message (often truncated in job history, full here)
"Is the Log Reader alive?"Publication → Agents tab → Log Reader Agent status + last action
"When did the snapshot last run?"Agents tab → Snapshot Agent history

Warnings & thresholds

Per subscription, the Warnings tab lets you enable thresholds that turn the status amber and can raise alerts (they map to the canned alerts configured on the Alerts page):

  • Latency exceeds — default 30 s (transactional). Tune per business SLA, not per wishful thinking.
  • Subscription expiration — warn at % of retention. Set to warn days before the 336 h cliff.
  • Merge sync duration / rows per second — merge-specific slowness detectors.
⚠ Replication Monitor is a viewer, not a monitor

It polls only while someone has it open — it will never page you (risk Monitoring gap). Production monitoring needs the alert jobs and queries wired to your alerting platform; Replication Monitor is the triage UI you open after the page.

Monitoring without the GUI

Everything the Monitor shows comes from distributor procs you can script (full list on Distributor commands):

USE distribution;

-- one row per publication with worst latency/status rollup
EXEC sp_replmonitorhelppublication @publisher = N'PUB01';

-- one row per subscription: status, latency, last sync
EXEC sp_replmonitorhelpsubscription @publisher = N'PUB01', @publication_type = 0;

-- queue depth for one subscription (the Undistributed Commands tab)
EXEC sp_replmonitorsubscriptionpendingcmds
     @publisher = N'PUB01', @publisher_db = N'SalesDB', @publication = N'SalesPub',
     @subscriber = N'SUB01', @subscriber_db = N'SalesReporting', @subscription_type = 0;

status values in the monitor procs: 1 Started · 2 Succeeded · 3 In progress · 4 Idle · 5 Retrying · 6 Failed. Alert on 5 and 6; investigate 4 when latency grows (idle + growing queue = agent not picking up work).

Permissions

Replication Monitor does not require sysadmin: add support engineers to the replmonitor database role in the distribution database for read-only monitoring access — the supportable pattern for ops teams.
