Performance & latency tuning

Tune in this order: find the slow queue → fix the root cause → only then turn agent knobs. Agent parameters amplify a healthy pipeline; they cannot outrun a blocked subscriber or an undersized distributor.

Step 0 — locate the bottleneck

Use a tracer token to split the latency, then follow the three-queue model from the overview. Everything below is organized by which leg is slow.

Leg 1 slow — publisher → distributor (Log Reader)

CauseSignalFix
Giant transactionsOne xact_seqno with millions of commandsBatch publisher DML; set -MaxCmdsInTran 10000 on the Log Reader so delivery can start before the whole txn is harvested (note: trades strict atomicity at the subscriber)
Log file fragmentation / huge VLF countSlow log scans, slow recovery tooFix VLF layout (shrink + regrow log properly)
Publisher IO pressureHigh log read latency in sys.dm_io_virtual_file_statsStorage; consider a remote distributor to offload
Harvest batch too smallSteady small lag under high txn rateRaise -ReadBatchSize (default 500 txns) cautiously

Leg 2 slow — distributor → subscriber (Distribution Agent)

CauseSignalFix
Subscriber blockingAgent session waiting on locksRCSI at subscriber; move reports; see ⚠ Subscriber workload blocks agent
Row-by-row apply overheadHigh cmd count, low delivery rate, no waits-CommitBatchSize (default 100 txns) up to 1000; -SubscriptionStreams 4 for parallel apply (requires no out-of-order dependencies; errors roll back to serial)
Missing/odd indexes at subscriberHigh reads per applied commandSubscriber tables need their PK (always there) and not much else during catch-up; drop exotic subscriber-only indexes during bulk catch-up
Network latency to remote subscriberLow delivery rate, no server waits-UseOledbStreaming, bigger batches, or move to pull agent at the subscriber side of the WAN
Agent restarts/timeouts in a loopHistory shows same batch retriedFix the stuck command (see common errors) — don't tune around it

Distributor itself slow

  • Distribution DB on slow storage — every command is written once and read N times (N subscribers). Treat it like a busy OLTP database: fast storage, pre-sized files, no autogrow storms.
  • Bloated MSrepl_commands — cleanup can't keep up or immediate_sync keeps 2 weeks of history (see the @immediate_sync callout). A lean queue is a fast queue.
  • Cleanup job contention — see ⚠ Distribution cleanup blocking: reschedule, don't disable.
  • Too many agents on one box — each subscription = one distrib.exe process; hundreds of continuous agents may need agent consolidation (@independent_agent='false') or staggered schedules.

Design-level levers (bigger than any knob)

  • Publish less: row/column filters, and don't publish audit/log tables nobody reads at the subscriber.
  • Replicate the execution of stored procedures for mass maintenance operations (article type proc exec): one proc call replicates instead of a million row commands. Requires determinism at the subscriber — use deliberately.
  • Multiple publications per database to give independent agents to hot vs. cold tables — one table's backlog stops dragging everything.
  • Pull agents move apply CPU to subscribers when distributor CPU is the ceiling.
  • Initialize from backup for new large subscribers instead of monster snapshots.

Catch-up playbook (after an outage)

  1. Confirm root cause fixed and agents running; backlog draining (queue count decreasing over 2–3 samples).
  2. Estimate drain time: pending commands ÷ current delivery rate (both from sp_replmonitorsubscriptionpendingcmds / history). Communicate it.
  3. If too slow: temporary profile with CommitBatchSize 1000 / CommitBatchThreshold 2000, SubscriptionStreams 4; pause heavy subscriber reports; verify cleanup isn't fighting the agents.
  4. If drain time exceeds retention runway (subscription will expire first): raise publication @retention now, or accept reinitialization and plan it.
  5. Afterwards: revert profiles to defaults; post a tracer token to confirm steady-state; write down the numbers for next time.
