Incident triage — step by step from symptom to fix

The complete diagnostic workflow for a replication incident: what to look at, in which order, on which server, and what to do when you find an error. Follow it top to bottom; each branch hands you off to the detailed page for that scenario.

The four symptom classes and where each one sends you. Details for every box follow below.

Step 1 — Classify the symptom (30 seconds)

Ask the reporter (or the alert) one question: what is actually wrong?

They sayClassGo to
"Replication failed / an alert fired / agent red in Monitor"ErrorSteps 2–4 below
"Subscriber data is stale / reports are behind" (no error visible)Latency / stalledStep 2, then Is it moving?
"Rows are different / missing at the subscriber"Data mismatchStep 7 below
"Disk filling on publisher/distributor" / log growth alertGrowthStep 8 below

If you don't know the topology yet, run Topology Discovery first — five minutes spent there prevents fixing the wrong server.

Step 2 — Take a status snapshot (which agent, which state)

USE distribution;
-- status per subscription: 6 = FAILED, 5 = RETRYING, 4 = idle, 3 = running, 2 = succeeded, 1 = started
EXEC sp_replmonitorhelpsubscription @publisher = N'PUB01', @publication_type = 0;

-- continuous agents that should be running but aren't
SELECT j.name
FROM msdb.dbo.sysjobs j
JOIN msdb.dbo.syscategories c ON c.category_id = j.category_id
WHERE c.name IN ('REPL-LogReader','REPL-Distribution') AND j.enabled = 1
  AND NOT EXISTS (SELECT 1 FROM msdb.dbo.sysjobactivity a
                  WHERE a.job_id = j.job_id
                    AND a.start_execution_date IS NOT NULL AND a.stop_execution_date IS NULL);
  • Status 6 (failed) or 5 (retrying) → you have your agent; go to Step 3.
  • Agent stopped but no failure → start it, watch one session complete, then verify flow (Is it moving?). Find why it was stopped before closing the ticket.
  • Everything "idle / succeeded" but symptom persists → not an agent error; jump to Is it moving? or Step 7/8 per the symptom class.
  • Pull subscriptions: remember their agent state and history live at the subscriber — this snapshot at the distributor shows less for them.

Step 3 — Get the FULL error text (not the job history summary)

USE distribution;
-- the real error, untruncated, newest first
SELECT TOP 20 time, source_name,
       error_text = CONVERT(nvarchar(4000), error_text)
FROM dbo.MSrepl_errors
ORDER BY time DESC;

-- the sessions around it (what the agent was doing)
SELECT TOP 20 h.start_time, h.comments, h.error_id
FROM dbo.MSdistribution_history h
JOIN dbo.MSdistribution_agents a ON a.id = h.agent_id
WHERE a.publication = N'SalesPub'
ORDER BY h.start_time DESC;

Record three things from the error text: the error number, the server it occurred on (an agent touches up to three servers — the message names the failing side), and any xact_seqno / command id mentioned. If job history is all you have and it's truncated, rerun the agent with -Output C:\Temp\agent.log -OutputVerboseLevel 2 temporarily.

Step 4 — If there is an error: decode and match it

  1. Decode the failing command (when the error references a transaction): 
    EXEC distribution.dbo.sp_browsereplcmds
     @xact_seqno_start = '0x0000002B000001D8000A',   -- from the error text
     @xact_seqno_end   = '0x0000002B000001D8000A';
-- output: the exact {CALL sp_MSins_dboOrders(...)} with table + PK values
    Now you know the table and row involved — half the diagnosis.
  2. Match the error number on the Common Errors page — it covers 20598 (row not found), 2601/2627 (duplicates), log full, 18456 (logins), 21074 (expired), query timeouts, Log Reader errors, 548 (identity ranges), 22815 (P2P conflict), snapshot OS errors, and schema breakages, each with cause → triage → fix.
  3. Not listed? Search the error number together with the agent name. Before acting on advice, check it against the risk checklist — several popular "fixes" (sp_repldone resets, -SkipErrors, disabling cleanup) are listed there as incident causes.
  4. Collect before escalating (to senior/vendor): topology map, full error text, decoded command, agent history for the last 24 h, queue depths, and the watermark report. That set answers the first ten questions any escalation will ask.

Step 5 — Fix forward, with guardrails

  • Prefer the smallest true fix: repair the one subscriber row, fix the one permission, clear the one block — then let the agent continue. The pipeline is ordered; once the head command succeeds, the rest usually drains on its own.
  • Before any reinitialization, skip, or watermark change, check the risk checklist entry for that action and do the reinit impact math (snapshot time + subscriber app outage).
  • Make one change at a time and watch one full agent session after each — replication's retry behavior makes multi-change debugging unreadable.

Step 6 — Verify and close

  1. Flow restored: post a tracer token; confirm it arrives within SLA, and the backlog is shrinking (queue checks).
  2. Convergence intact: if the incident involved skipped commands, manual row repairs, or subscriber-side writes, run sp_publication_validation (or tablediff) on the affected articles.
  3. Document: error number, root cause, fix, and the queries that found it — into the runbook. Next quarter's engineer (possibly you) starts from your note instead of from zero.

Step 7 — Data mismatch branch (no agent error)

  1. Confirm the object/rows are supposed to be there: Discovery Step 6 — is the table an article at all? Does a row filter exclude those rows, or a column filter that column?
  2. Check subscription state: inactive/expired subscription (status 0) means nothing has flowed for a long time — see error 21074 handling.
  3. Quantify the drift: sp_publication_validation @rowcount_only = 2, or tablediff.exe for row-level detail and a generated repair script.
  4. Find the writer: if subscriber rows were modified locally, identify the process (Extended Events audit on the subscriber table) — otherwise the mismatch returns.
  5. Repair: targeted (tablediff fix script) when drift is small; reinitialize when it isn't. Validate afterwards.

Step 8 — Growth branch (log or distribution DB filling)

  1. Publisher log growing: SELECT log_reuse_wait_desc FROM sys.databases WHERE name='SalesDB' → if REPLICATION, the Log Reader is behind or orphaned → log-full runbook, and LSN deep dive to see exactly where it's stuck.
  2. Distribution DB growing: which subscription holds retention back? (sp_replmonitorsubscriptionpendingcmds per subscription; a dead subscriber keeps everything). Check cleanup job history. Risk entries: Distribution database growth, Cleanup blocking, and the immediate_sync trap on the publication page.
  3. Snapshot folder growing: old snapshot subfolders not cleaned → check "Expired subscription clean up" and reinit habits.
