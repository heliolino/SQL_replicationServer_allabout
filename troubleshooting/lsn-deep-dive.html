LSNs & xact_seqno — the pipeline's coordinate system

Every replication watermark, error message, and ordering guarantee is expressed in Log Sequence Numbers. This page explains what they are, how to read the publisher's current position, how to find which transaction and which object a given LSN points at on the distributor — and how to work out what is preventing it from moving.

What an LSN is (and why replication runs on them)

  • Every record written to a database's transaction log gets a unique, strictly increasing address: the LSN, three hex parts — VLF : log block : record, e.g. 0000002B : 000001D8 : 0003.
  • Transactional replication is log-driven: the Log Reader walks the log by LSN, and a transaction's identity in the pipeline is the LSN of its commit record, stored at the distributor as the 10-byte xact_seqno (the three LSN parts concatenated, zero-padded — 0x0000002B000001D80003). Same number, two notations.
  • Three guarantees hang on it:
    1. Ordering — agents deliver in xact_seqno order, so the subscriber is always a consistent past snapshot of the publisher.
    2. Exactly-once — each stage records the highest LSN it has safely processed (its watermark) and restarts from there after any interruption.
    3. Log truncation safety — the publisher's log cannot truncate past the oldest LSN not yet harvested; that's why a stuck Log Reader fills the disk (risk ⚠ Log Reader latency).
delivered harvested, queued committed, not yet harvested

Step 1 — Read the publisher's current LSN position

USE SalesDB;

-- A. the Log Reader's two watermarks + backlog, one row per published DB
EXEC sp_replcounters;
--   replbeginlsn = oldest distributed LSN not yet acknowledged-for-truncation
--   replnextlsn  = where the Log Reader resumes  ← "current position"
--   replicated transactions = committed txns between those marks (backlog)

-- B. the same two marks, labeled, plus the oldest open transaction
DBCC OPENTRAN (N'SalesDB');
--   "Replicated Transaction Information:
--      Oldest distributed LSN     : (43:472:3)       ← decimal (VLF:block:record)
--      Oldest non-distributed LSN : (43:514:1)"      ← first txn NOT yet harvested

-- C. list every committed-but-unharvested transaction with its LSNs
EXEC sp_repltrans;    -- xdesid = transaction id, LSN pairs (begin/commit), newest at the bottom
⚠ Decimal vs hex — don't compare apples to apples-in-hex

DBCC OPENTRAN prints LSNs in decimal (43:472:3); sp_replcounters, sp_repltrans and all distributor tables use hex (0x0000002B000001D80003 — and 43 = 0x2B). Convert before comparing: SELECT CONVERT(varbinary(4), 43) -- 0x0000002B per part, or format the three parts as 8+8+4 hex digits and concatenate.

Step 2 — Find that LSN on the distributor: which transaction, which object

USE distribution;

-- A. does this xact_seqno exist in the queue, and when did it arrive?
SELECT t.xact_seqno, t.entry_time,
       commands_in_txn = (SELECT COUNT(*) FROM dbo.MSrepl_commands c
                          WHERE c.xact_seqno = t.xact_seqno
                            AND c.publisher_database_id = t.publisher_database_id)
FROM dbo.MSrepl_transactions t
WHERE t.xact_seqno = 0x0000002B000001D80003;      -- your LSN in hex

-- B. WHICH OBJECTS (articles) does that transaction touch?
SELECT DISTINCT a.article, a.source_owner, a.source_object, a.destination_object
FROM dbo.MSrepl_commands c
JOIN dbo.MSarticles a ON a.article_id = c.article_id
                     AND a.publisher_db = (SELECT publisher_db FROM dbo.MSpublisher_databases
                                           WHERE id = c.publisher_database_id)
WHERE c.xact_seqno = 0x0000002B000001D80003;

-- C. the exact commands (statement + PK values) at that LSN
EXEC sp_browsereplcmds
     @xact_seqno_start = '0x0000002B000001D80003',
     @xact_seqno_end   = '0x0000002B000001D80003';
-- → {CALL [sp_MSins_dboOrders] (1234, N'ACME', ...)}  — object AND row identified

-- D. neighborhood view: what sits just before/after (useful when the agent is stuck "near" an LSN)
SELECT TOP 20 xact_seqno, entry_time
FROM dbo.MSrepl_transactions
WHERE xact_seqno >= 0x0000002B000001D80000
ORDER BY xact_seqno;

Step 3 — The watermark report: where is every stage, in one result?

USE distribution;
SELECT
  stage = 'newest harvested (Log Reader wrote)',
  seqno = MAX(t.xact_seqno), at_time = MAX(t.entry_time)
FROM dbo.MSrepl_transactions t
UNION ALL
SELECT 'last read by Log Reader (its own history)',
       MAX(h.xact_seqno), MAX(h.time)
FROM dbo.MSlogreader_history h
UNION ALL
SELECT 'last delivered per subscription: ' + a.name,
       MAX(h.xact_seqno), MAX(h.time)
FROM dbo.MSdistribution_history h
JOIN dbo.MSdistribution_agents a ON a.id = h.agent_id
GROUP BY a.name;

-- publisher side (run there):  EXEC sp_replcounters;          → replnextlsn
-- subscriber side (run there): SELECT publication, transaction_timestamp
--                              FROM dbo.MSreplication_subscriptions;  → applied bookmark

Line the numbers up (they're all the same hex coordinate system). The pipeline is healthy when publisher replnextlsn ≥ newest harvested ≥ last delivered ≥ subscriber bookmark and all of them advance between two samples — the first one that freezes names the broken stage (same logic as Is it moving?, now with exact coordinates).

Step 4 — What is preventing the LSN from moving?

Case A — publisher watermark frozen (Log Reader can't advance)

-- is a monster transaction being scanned? the log reader's in-memory state:
SELECT * FROM sys.dm_repl_traninfo;
-- cmds_in_tran climbing for one transaction = a huge txn being harvested; wait or
-- consider -MaxCmdsInTran (see performance page). Also: DBCC OPENTRAN for an
-- old OPEN transaction — an uncommitted txn is invisible to replication but pins the log.

-- articles as the log reader sees them (cache problems show here)
SELECT * FROM sys.dm_repl_articles;
  • Agent down / erroring — job history + MSlogreader_history.comments; 18752 means another session stole its sp_replcmds slot (fix).
  • Giant transaction — sys.dm_repl_traninfo shows it being chewed; watermark jumps only when the whole txn is harvested.
  • Broken log chain (restore over a published DB) — errors 18768/"specified LSN is invalid": the watermark points at log that no longer exists → usually rebuild (risk ⚠ Restoring a published database).

Case B — delivery watermark frozen (queue grows, subscriber bookmark static)

  • Retry loop on one command: the agent re-attempts the same xact_seqno each session (visible in history). Decode it (Step 2C) → match on Common Errors. The ordered pipeline means this single LSN dams everything behind it.
  • Blocked apply at the subscriber: sys.dm_exec_requests where program_name LIKE '%distrib%' → blocking_session_id.
  • Agent stopped / schedule — pull agents especially: the job lives at the subscriber.
  • Subscription inactive (status 0 in MSsubscriptions): nothing will ever be delivered — reinit required (error 21074).

Case C — truncation point frozen (log grows although replication "works")

  • The truncation point is the older of (a) the harvest watermark and (b) what's still needed for undelivered subscribers when immediate_sync/retention keep commands. One dead subscription can thus pin the publisher's log indirectly — find it with the per-subscription delivered watermarks from Step 3 (the oldest one is your culprit).
  • Verify what the engine itself is waiting for: SELECT log_reuse_wait_desc FROM sys.databases WHERE name='SalesDB' — if it says REPLICATION with no live replication, see the orphaned-metadata runbook in Common Errors.
🛑 Moving watermarks by hand

Exactly one supported command moves the harvest watermark: sp_repldone — and the Log Reader is its only legitimate caller. The manual reset (@xactid=NULL, @xact_seqno=NULL, @numtrans=0, @time=0, @reset=1) declares everything harvested: the log frees, and every subscriber silently misses whatever hadn't been delivered — mandatory reinitialization. It is a disk-space-emergency tool, never a latency fix. Full context on the publisher commands page.
