Common errors — cause, triage, fix

The errors a replication support engineer actually meets, ordered by how often they page you. Every fix below assumes you've located the failing agent and read its full error text (MSrepl_errors / agent session history — not just job history).

Error 20598 — "The row was not found at the Subscriber"

AgentDistribution Agent — stops, retries the same transaction forever
CauseA replicated UPDATE/DELETE targets a row that doesn't exist at the subscriber: someone deleted/changed subscriber data directly, a previous skip, or a bad reinit
TriageIdentify the failing command: take xact_seqno and command_id from the error detail, decode with sp_browsereplcmds → gives you table + PK values
FixRe-insert the missing row at the subscriber (copy from publisher by PK) → agent proceeds. If drift is broad: tablediff.exe -f to generate a repair script, or reinitialize the subscription
Avoid-SkipErrors 20598 as a "fix" — it converts a visible stop into silent divergence. Acceptable only to restore flow during a major incident, followed by validation + repair

Errors 2601 / 2627 — duplicate key at the Subscriber

The mirror image of 20598: a replicated INSERT finds the row already there (local writes, double-applied batch after an unclean agent stop). Same triage via sp_browsereplcmds; fix by deleting/merging the conflicting subscriber row. Recurring 2627s on identity PKs at a writable subscriber = identity range misconfiguration — see error 548.

Log file full — log_reuse_wait_desc = REPLICATION

SymptomPublication DB log grows despite log backups; eventually 9002 (log full), writes stop
CauseLog Reader not harvesting: agent down/failing, giant transaction in progress, or replication/CDC remnants after a sloppy teardown
Triagesp_replcounters (pending txns?), Log Reader job history, DBCC OPENTRAN (oldest replicated txn), is the DB even published? SELECT is_published, is_cdc_enabled FROM sys.databases
Fix (agent down)Fix and start the Log Reader; log clears at next backup/checkpoint after harvest catches up
Fix (orphaned metadata, replication NOT wanted)EXEC sp_removedbreplication N'SalesDB'; — and if the marker persists, the last-resort watermark reset: 
EXEC sp_repldone @xactid = NULL, @xact_seqno = NULL,
     @numtrans = 0, @time = 0, @reset = 1;
EXEC sp_replflush;
-- any existing subscribers are now inconsistent → must be reinitialized

Error 18456 / 18452 — agent login failures

After password rotations or permission hardening. Read the state code in the error (state 5 = unknown login, state 38 = can't open database). Fix with the credential-rotation runbook — via the sp_change*_agent procs, not by editing job steps. Remember each agent makes multiple connections (distributor + publisher + subscriber): the failing side is named in the message.

Error 21074 / "subscription(s) have been marked inactive"

Retention expired while a subscriber was down (or the Distribution Agent was stopped long enough). MSsubscriptions.status = 0. There is no shortcut: reinitialize (sp_reinitsubscription + snapshot, or initialize from backup). Prevention is the whole game — alert on "days since last sync" vs retention (see Alerts).

"Query timeout expired" — the agent retry loop

  1. Find what the apply statement waits on at the subscriber: sys.dm_exec_requests where program_name LIKE '%distrib%' → blocking session? long IO?
  2. Fix the wait: kill/relocate the blocking report, add the missing index, resolve autogrowth stalls.
  3. Only then consider a profile with larger -QueryTimeout for genuinely long applies (huge batches on slow links).

Error 548 — identity range check constraint (merge)

"The insert failed. It conflicted with an identity range check constraint…" — the node exhausted its allocated identity range offline. Run the Merge Agent (gets a fresh range), or at the publisher sp_adjustpublisheridentityrange. Then resize ranges so the longest realistic offline period fits (@identity_range on the article). Details: ⚠ Merge identity range exhaustion on the risk checklist.

Error 22815 — peer-to-peer conflict

By design, agents stop. The message names the two originator ids and the row. Decide the business-correct winner, fix the losing peer's row manually, restart agents — then fix the application's write partitioning, which is the actual defect. Never flip @p2p_continue_onconflict as a permanent "fix" (why).

OS error 5 / 3 — snapshot delivery failures

"The process could not read file \\DIST\ReplData\…\Orders_1.bcp" — access denied (5) or path not found (3). Almost always: snapshot folder configured with a local path while a pull agent runs elsewhere, or NTFS/share ACLs missing for the agent account. Test as the agent account (runas), fix path to UNC / grant read. See ⚠ Snapshot folder permissions.

Schema-change breakages

  • "Invalid column name" at subscriber right after a deployment → DDL replicated out of order with DML, or replicate_ddl=0 and schemas drifted. Compare article schema both sides; worst case re-snapshot the article.
  • Cannot ALTER a published column: some DDL is blocked while published — drop the article, alter, re-add + re-snapshot.
  • "Cannot drop the table because it is being used for replication" (3724) — the table is an article; remove it from the publication first.

The generic triage ladder (when the error is new to you)

  1. Which agent? Replication Monitor or the watchdog queries → failing/retrying subscription.
  2. Full error text: agent session detail or MSrepl_errors (job history truncates).
  3. Which of the three queues is backing up? (overview model) — tells you which server to log into.
  4. Reproduce understanding: decode the exact failing command (sp_browsereplcmds) before changing anything.
  5. Fix forward (repair row, fix perms, clear block) rather than skip/reinit, unless retention math says reinit is already inevitable.
  6. Afterwards: tracer token for flow, validation for convergence, note in the runbook.
