Is transactional replication actually moving?

A tracer token is the headline test — but it needs the pipeline to carry it, takes minutes, and tells you nothing about a backlog already queued ahead of it. These are the six independent checks that prove (or disprove) movement from metadata alone, each sampled twice a few minutes apart: movement is always a delta, never a single snapshot.

The four watermarks checked below — ①②③④ map to checks 1–4.

Check 0 — Is there anything to move?

A quiet system looks identical to a dead one. Before anything else, confirm change volume exists — or create some with a canary write:

-- any committed, not-yet-harvested transactions right now?
USE SalesDB;
EXEC sp_repltrans;                -- rows = work waiting for the Log Reader; empty = nothing pending

-- canary: touch a published row (use a known test/heartbeat row, not real data)
UPDATE dbo.ReplHeartbeat SET last_beat = SYSUTCDATETIME() WHERE id = 1;
-- then check its arrival at the subscriber (Check 5)
✅ Build the heartbeat table once, thank yourself forever

A one-row table (id int PK, last_beat datetime2) included as an article, updated by a SQL Agent job every minute at the publisher, turns "is it moving?" into a single query at the subscriber: SELECT DATEDIFF(SECOND, last_beat, SYSUTCDATETIME()) FROM dbo.ReplHeartbeat — a continuous, end-to-end lag gauge that works even when agents lie idle and no users are writing.

Check 1 — Publisher harvest watermark (Log Reader leg)

EXEC sp_replcounters;
-- watch three columns between samples:
--   replicated transactions = backlog waiting for the Log Reader  (should shrink or stay ~0)
--   replication rate trans/sec = harvest throughput               (should be > 0 under load)
--   replnextlsn = next LSN the Log Reader will read               (MUST advance if backlog > 0)
Between two samples…Verdict
backlog ≈ 0, rate ≈ 0, replnextlsn static✅ Nothing to harvest — quiet, not stuck (confirm with canary)
backlog > 0 and shrinking, replnextlsn advancing✅ Harvesting — catch-up in progress
backlog > 0 and flat/growing, replnextlsn static❌ Log Reader stuck → its job state & history, then LSN deep dive

Check 2 — Distribution queue intake (newest queued command)

USE distribution;
SELECT newest_queued_seqno = MAX(xact_seqno),
       newest_entry_time   = MAX(entry_time),
       queued_txns         = COUNT(*)
FROM dbo.MSrepl_transactions WITH (NOLOCK)
WHERE publisher_database_id = 1;    -- see sp_helpdistpublisher / MSpublisher_databases
  • newest_entry_time advancing → Log Reader is writing into the queue (leg 1 confirmed end-to-end).
  • Static while the publisher has backlog → the Log Reader can read but not write: distributor full/blocked, connectivity, or agent down — check its history.

Check 3 — Delivery watermark (Distribution Agent leg, per subscription)

USE distribution;
SELECT a.name,
       last_delivered_seqno = h.xact_seqno,
       h.delivered_commands, h.current_delivery_rate, h.comments, h.time
FROM dbo.MSdistribution_agents a
CROSS APPLY (SELECT TOP 1 * FROM dbo.MSdistribution_history h
             WHERE h.agent_id = a.id ORDER BY h.timestamp DESC) h
WHERE a.subscriber_db <> 'virtual'
ORDER BY a.name;
  • xact_seqno advancing toward Check 2's newest seqno, delivered_commands increasing → ✅ delivering.
  • comments stuck on "No replicated transactions are available" while Check 2 shows new queued txns → agent polling the wrong state or filtered publication quirk — verify the subscription's pending commands (next line).
  • Same xact_seqno both samples with pending work → ❌ stuck: retry loop (read MSrepl_errors) or blocked at the subscriber (Check 4).
  • Backlog number itself: sp_replmonitorsubscriptionpendingcmds twice — shrinking = draining; growing = intake > delivery (slow, not stopped — go to performance).

Check 4 — Subscriber applied bookmark

-- the subscriber's own record of the last applied transaction
SELECT publication, transaction_timestamp AS applied_up_to_seqno, [time] AS last_sync
FROM dbo.MSreplication_subscriptions;

-- is an agent even connected and working right now?
SELECT s.session_id, s.program_name, r.status, r.command,
       r.wait_type, r.blocking_session_id
FROM sys.dm_exec_sessions s
LEFT JOIN sys.dm_exec_requests r ON r.session_id = s.session_id
WHERE s.program_name LIKE '%distrib%';
  • transaction_timestamp advancing → ✅ applies are landing (the definitive subscriber-side proof).
  • Agent session present but blocking_session_id > 0 → delivery blocked by local workload → risk ⚠ Subscriber blocking.
  • No distrib session at all (push) → the agent isn't reaching this server: network/login — check from the distributor side.

Check 5 — The canary arrives (end-to-end truth)

SELECT last_beat,
       lag_seconds = DATEDIFF(SECOND, last_beat, SYSUTCDATETIME())
FROM dbo.ReplHeartbeat;
-- lag ≈ heartbeat interval → flowing; lag growing minute by minute → stalled upstream

This plus a tracer token are the two end-to-end proofs; everything above tells you which stage to blame when they fail.

Check 6 — Perfmon counters (live, no queries)

  • SQLServer:Replication Log Reader → Logreader:Delivered Cmds/sec > 0 under load = harvesting.
  • SQLServer:Replication Dist. → Dist:Delivered Cmds/sec > 0 = applying. Both at 0 while users write = stalled.

Reading the results — which stage is broken?

① Harvest② Intake③ Delivery④ AppliedDiagnosis → next page
✅✅✅✅Moving. If users still complain: expectation vs SLA, or wrong subscriber/database being checked
❌———Log Reader stuck → job state/history, then LSN deep dive to find the pinning transaction
✅❌——Log Reader can't write to distributor → distributor health, connectivity, distribution DB full/blocked
✅✅❌—Distribution Agent stuck → MSrepl_errors (retry loop? → common errors), or agent stopped
✅✅✅ slow✅ slowMoving but outpaced → performance & latency catch-up playbook
✅✅✅❌Delivery "succeeds" but bookmark frozen → blocked applies at subscriber (Check 4 blocking query), or you're reading a different subscription DB than the agent writes
⚠ Two sampling pitfalls
  • One sample proves nothing. Every check above is a delta. A big queue with a fast drain is healthy; a tiny queue that never changes is dead.
  • "No replicated transactions are available" is good news, not an error — it's the Distribution Agent's idle message. The matching Log Reader idle message is "No replicated transactions…" in its own history. Idle + empty queues + canary arriving = healthy and quiet.
