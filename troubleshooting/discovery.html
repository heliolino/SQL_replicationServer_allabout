Topology discovery — mapping an unknown replication environment

You've been handed a server (or an incident) with no documentation. This page is the step-by-step interrogation: which replication type is running, which server is Publisher, Distributor, and Subscriber, what the publications and subscriptions are, and whether the publisher ships all objects or only a few filtered articles. Every step is a copy-paste query; run them top to bottom and you'll have the full map in ~10 minutes.

✅ Where to start when you only have one server name

Start on whatever server you were given — Step 1 tells you which role(s) it plays. The distributor is the best vantage point (it sees the whole topology), so as soon as any query reveals the distributor's name, jump there and run Steps 3–5 from it.

Step 1 — What roles does THIS server play?

-- 1a. database-level flags: which databases publish or distribute?
SELECT name,
       is_published        AS publishes_tran_or_snap,   -- transactional / snapshot publisher DB
       is_merge_published  AS publishes_merge,          -- merge publisher DB
       is_distributor      AS is_distribution_db        -- this DB *is* a distribution DB
FROM sys.databases
WHERE database_id > 4
ORDER BY name;

-- 1b. is this instance configured as (or pointed at) a distributor?
EXEC sp_get_distributor;
-- installed = 1              → this instance knows a distributor
-- "distribution server"      → WHO the distributor is (itself = local distributor)
-- "distribution db installed"= 1 → the distribution DB lives HERE (this box IS the distributor)

-- 1c. is this server a SUBSCRIBER? (look for subscription metadata in each DB)
EXEC sp_MSforeachdb N'
IF OBJECT_ID(''[?].dbo.MSreplication_subscriptions'') IS NOT NULL
    SELECT DB_NAME = ''?'', publisher, publisher_db, publication, distribution_agent
    FROM [?].dbo.MSreplication_subscriptions;';

-- 1d. corroborate with the agent jobs present on this instance
SELECT c.name AS category, COUNT(*) AS jobs
FROM msdb.dbo.sysjobs j
JOIN msdb.dbo.syscategories c ON c.category_id = j.category_id
WHERE c.name LIKE 'REPL-%'
GROUP BY c.name;
-- REPL-LogReader here        → publisher's log is read from here (distributor side)
-- REPL-Distribution here     → push agents (distributor) or pull agents (subscriber)
-- REPL-Snapshot / REPL-Merge → snapshot generation / merge sync runs here
FindingConclusion
is_published or is_merge_published = 1 on any DBThis server is a Publisher; those DBs are publication databases
sp_get_distributor → "distribution db installed" = 1This server is the Distributor (a DB named distribution — or similar — exists locally)
sp_get_distributor → distribution server ≠ @@SERVERNAMERemote distributor: note that name, go run Steps 3–5 there
MSreplication_subscriptions rows in a DBThis server is a Subscriber; the rows name its publisher & publication
Several of the above at onceNormal — one instance often holds two or three roles (e.g. publisher + local distributor)

Step 2 — Which replication TYPE is in use?

USE distribution;
SELECT publisher_db,
       publication,
       publication_type = CASE publication_type
                            WHEN 0 THEN 'Transactional'
                            WHEN 1 THEN 'Snapshot'
                            WHEN 2 THEN 'Merge'
                          END,
       immediate_sync, allow_pull, allow_push, retention
FROM dbo.MSpublications
ORDER BY publisher_db, publication;

USE SalesDB;   -- each DB with is_published / is_merge_published = 1

-- transactional vs snapshot
SELECT name AS publication,
       repl_freq = CASE repl_freq WHEN 0 THEN 'continuous → TRANSACTIONAL'
                                  WHEN 1 THEN 'scheduled  → SNAPSHOT' END,
       immediate_sync, enabled_for_p2p = NULL  -- see sp_helppublication for p2p flag
FROM dbo.syspublications;

-- friendly view incl. the P2P flag:
EXEC sp_helppublication;   -- column 'enabled_for_p2p' = 1 → PEER-TO-PEER

-- merge publications live in a different catalog:
SELECT name AS merge_publication, retention, priority = NULL
FROM dbo.sysmergepublications;
  • Transactional: publication_type = 0 / repl_freq = 0, a REPL-LogReader job exists for the DB. Details: Transactional.
  • Snapshot: publication_type = 1 / repl_freq = 1, no Log Reader job for that DB. Details: Snapshot.
  • Merge: rows in sysmergepublications, articles carry a rowguid column, triggers named MSmerge_ins/upd/del_* on the tables. Details: Merge.
  • Peer-to-peer: transactional with enabled_for_p2p = 1 in sp_helppublication — and the same publication exists on multiple "publishers" that subscribe to each other. Details: Peer-to-Peer.
  • Updatable subscriptions (legacy): a REPL-QueueReader job exists, MSsubscriptions.update_mode > 0 — flag for migration.

Step 3 — Map all three servers (the full topology)

USE distribution;
SELECT
    publisher      = pub_srv.name,
    p.publisher_db,
    p.publication,
    publication_type = CASE p.publication_type
                         WHEN 0 THEN 'Transactional' WHEN 1 THEN 'Snapshot' WHEN 2 THEN 'Merge' END,
    subscriber     = sub_srv.name,
    s.subscriber_db,
    sub_mode       = CASE s.subscription_type WHEN 0 THEN 'PUSH (agent job at distributor)'
                                              ELSE 'PULL (agent job at subscriber)' END,
    sub_status     = CASE s.status WHEN 0 THEN 'INACTIVE (needs reinit!)'
                                   WHEN 1 THEN 'subscribed' WHEN 2 THEN 'active' END
FROM dbo.MSpublications p
JOIN dbo.MSsubscriptions s ON s.publication_id = p.publication_id
JOIN sys.servers pub_srv   ON pub_srv.server_id = p.publisher_id
JOIN sys.servers sub_srv   ON sub_srv.server_id = s.subscriber_id
WHERE s.subscriber_db <> 'virtual'          -- filters out internal anonymous/virtual rows
GROUP BY pub_srv.name, p.publisher_db, p.publication, p.publication_type,
         sub_srv.name, s.subscriber_db, s.subscription_type, s.status
ORDER BY publisher, p.publication, subscriber;

Cross-checks from the other two vantage points (useful when you suspect metadata drift):

-- at the PUBLISHER: who distributes for me, and who subscribes?
EXEC sp_helpdistributor;        -- distributor name + distribution DB + snapshot folder
USE SalesDB;
EXEC sp_helpsubscription;       -- per article: subscriber, destination db, status

-- at the SUBSCRIBER: who feeds this database?
SELECT publisher, publisher_db, publication,
       subscription_type,       -- 0 push, 1 pull, 2 anonymous
       distribution_agent, time AS last_sync_time
FROM dbo.MSreplication_subscriptions;

Step 4 — Find the publications and what they contain

-- publications with their key options
EXEC sp_helppublication;
-- columns worth reading: status (active?), retention (hours),
-- immediate_sync (distribution DB bloat flag), allow_push/allow_pull, enabled_for_p2p

-- every article of one publication, with destination mapping
EXEC sp_helparticle @publication = N'SalesPub';
-- columns: article, source object, destination object/owner,
-- ins/upd/del commands, pre_creation_cmd, filter (row filter view if any)

Step 5 — Find the subscriptions and their agents

USE distribution;
-- subscription → agent job name mapping (what to start/stop/read history for)
SELECT a.name AS agent_job_name,
       a.publisher_db, a.publication,
       a.subscriber_db,
       local_job = a.local_job          -- 1 = push job in THIS msdb; 0 = pull job at subscriber
FROM dbo.MSdistribution_agents a
ORDER BY a.publication, a.subscriber_db;

-- merge equivalent: dbo.MSmerge_agents

For pull subscriptions (local_job = 0) the job and its history live in the subscriber's msdb — log into the subscriber to control it (see push vs pull).

Step 6 — Full database or a few articles? Filters?

-- 6a. published vs NOT-published tables, side by side
SELECT s.name + N'.' + t.name AS table_name,
       published = CASE WHEN a.objid IS NOT NULL THEN 'YES (' + a.name + ')' ELSE 'no' END
FROM sys.tables t
JOIN sys.schemas s ON s.schema_id = t.schema_id
LEFT JOIN dbo.sysarticles a ON a.objid = t.object_id
WHERE t.is_ms_shipped = 0
ORDER BY published DESC, table_name;
-- all YES → effectively whole-database publishing; mixed → selective articles

-- 6b. which articles have ROW filters (horizontal subset)?
SELECT name AS article, filter_clause
FROM dbo.sysarticles
WHERE filter_clause IS NOT NULL AND LEN(filter_clause) > 0;

-- 6c. which articles have COLUMN filters (vertical subset)?
SELECT a.name AS article,
       published_cols = COUNT(ac.colid),
       total_cols     = (SELECT COUNT(*) FROM sys.columns c WHERE c.object_id = a.objid)
FROM dbo.sysarticles a
JOIN dbo.sysarticlecolumns ac ON ac.artid = a.artid
GROUP BY a.name, a.objid
HAVING COUNT(ac.colid) <
       (SELECT COUNT(*) FROM sys.columns c WHERE c.object_id = a.objid);
-- rows returned = articles that do NOT ship every column

-- 6d. non-table articles (procs, views, functions)
SELECT name AS article, type_desc =
       CASE type WHEN 1 THEN 'log-based table' WHEN 8 THEN 'proc execution'
                 WHEN 24 THEN 'serializable proc exec' WHEN 32 THEN 'proc schema only'
                 WHEN 64 THEN 'view schema only' WHEN 128 THEN 'function schema only'
                 ELSE CONVERT(varchar(10), type) END
FROM dbo.sysarticles WHERE type <> 1;

-- merge equivalents: dbo.sysmergearticles (column subset_filterclause = row filter)
⚠ Why this step matters in incidents

"The table is missing at the subscriber" is often not a failure at all — the table was never an article, or a row filter excludes the rows being searched for, or a column filter omits the column the report wants. Run 6a–6c before declaring data loss.

Step 7 — Write it down

Capture the output into a one-page map: servers + roles, publications (type, retention, immediate_sync), subscriptions (push/pull, agent job name & location, status), filtered articles. This is the document every other troubleshooting page assumes you have. Store it with the topology creation scripts.
