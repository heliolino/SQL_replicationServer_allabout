Peer-to-Peer Transactional Replication

Transactional replication arranged in a ring/mesh of equal nodes: every peer publishes and subscribes to every other peer. Reads scale out everywhere, writes are allowed everywhere — as long as the application partitions them. Enterprise Edition only.

☁ Not available on Azure SQL Managed Instance

Peer-to-peer topologies are not supported on MI (curiously, the initialize from lsn sync type P2P introduced still exists there, and the MI backup-initialization procedure borrows it). For multi-region writable copies with MI, look at failover groups for HA/DR, or one-way transactional replication per direction with application-level partitioning.

Every peer is Publisher + Subscriber + (usually) its own Distributor.

Conflict detection in depth

With @p2p_conflictdetection = 'true' (default when created via the wizard), every row carries a hidden $sys_p2p_cd_id column encoding the originator and version. On apply, the receiving peer compares versions: a mismatch means two peers changed the row independently → error 22815, agent stops (default @p2p_continue_onconflict = 'false').

🛑 Do not be tempted by @p2p_continue_onconflict = 'true'

It lets the highest-originator-id win and keeps going — which means silent divergence whenever your write partitioning is broken. The stop-on-conflict default is annoying but honest: it tells you the application wrote the same row in two places. Fix the partitioning; don't mute the detector. Microsoft's own guidance is to treat continue-on-conflict as a temporary measure while you repair the topology.

Operational rules

  • Partition writes. Each row (customer, region, tenant…) must have exactly one home node. Enforce in the app layer or with CHECK constraints per node.
  • Quiesce for topology changes: stop writes everywhere, let all queues drain (verify with tracer-like marker rows), then add/remove nodes or alter schema via sp_addpublication/wizard.
  • Restoring one peer = initialize it from a current peer's backup, then sp_addsubscription with @sync_type = 'replication support only' / initialize-with-backup patterns.
  • Monitor every edge. A 3-node mesh has 6 one-way pipelines; one lagging edge breaks the "everyone is current" assumption. Tracer tokens work per publication edge.

Minimal creation script (per node)

-- on each peer, after distributor setup and identical schema/data:
EXEC sp_replicationdboption @dbname = N'SalesDB', @optname = N'publish', @value = N'true';

EXEC sp_addpublication
     @publication = N'P2P_Sales',
     @publication_type = N'transactional',
     @allow_push = N'true',
     @enabled_for_p2p = N'true',                -- the switch that makes it P2P
     @p2p_conflictdetection = N'true',
     @p2p_originator_id = 1,                    -- unique per peer!
     @status = N'active';

EXEC sp_addarticle @publication = N'P2P_Sales',
     @article = N'Orders', @source_owner = N'dbo', @source_object = N'Orders';

-- then, per remote peer:
EXEC sp_addsubscription
     @publication = N'P2P_Sales',
     @subscriber = N'LON01', @destination_db = N'SalesDB',
     @subscription_type = N'Push',
     @sync_type = N'replication support only';  -- data already in place
