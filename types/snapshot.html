Snapshot Replication

The simplest type: copy everything, every time. No change tracking at all — the Snapshot Agent exports all articles in full, and the Distribution Agent replaces the subscriber's copy wholesale. It is also the initialization mechanism for every other replication type.

No Log Reader, no change tracking — the whole publication ships on every scheduled run.

When snapshot is the right answer

  • Data changes rarely or is refreshed wholesale anyway (price lists, reference/lookup tables, nightly-rebuilt dimensions).
  • It is acceptable for the subscriber copy to be stale between runs, and the total volume is small enough to copy in the window.
  • You want zero publisher-side overhead between runs — snapshot adds no triggers, no log marking, nothing continuous.
  • Large churn case: if 80% of rows change daily, shipping a snapshot nightly can be cheaper than replicating every change transactionally.

Mechanics in detail

  1. Snapshot Agent runs (scheduled or manual). It writes per-article schema scripts (.sch), constraint/index scripts (.dri/.idx), and BCP data files (.bcp) into a dated subfolder of the snapshot folder. For snapshot publications it holds shared locks on all articles for the duration of generation.
  2. Commands are queued. A small set of commands pointing at the snapshot files goes into the distribution database.
  3. Distribution Agent applies: per @pre_creation_cmd it drops (default), truncates, deletes from, or leaves the destination tables, re-creates schema, bulk-inserts the BCP files, then applies indexes/constraints.
  4. Until the next run, nothing happens — changes at the publisher are invisible to the subscriber.
⚠ Subscriber tables vanish during apply

With the default drop pre-creation command, the subscriber's tables are dropped and rebuilt during snapshot delivery. Queries running at that moment fail with "object does not exist"; subscriber-side extra indexes and triggers are lost unless scripted into post-snapshot scripts (@post_snapshot_script). Schedule applies off-hours and document any subscriber-side additions.

Minimal setup (T-SQL)

-- at the publisher (distributor already configured)
USE SalesDB;
EXEC sp_replicationdboption @dbname = N'SalesDB', @optname = N'publish', @value = N'true';

EXEC sp_addpublication
     @publication = N'RefDataPub',
     @publication_type = N'snapshot',    -- the only difference vs transactional here
     @sync_method = N'native',
     @repl_freq = N'snapshot',
     @status = N'active';

EXEC sp_addpublication_snapshot
     @publication = N'RefDataPub',
     @frequency_type = 4, @frequency_interval = 1,       -- daily
     @active_start_time = 10000;                          -- 01:00:00

EXEC sp_addarticle @publication = N'RefDataPub',
     @article = N'PriceList', @source_owner = N'dbo', @source_object = N'PriceList';

EXEC sp_addsubscription @publication = N'RefDataPub',
     @subscriber = N'SUB01', @destination_db = N'SalesReporting',
     @subscription_type = N'Push', @sync_type = N'automatic';

Monitoring a snapshot topology

  • Watch the Snapshot Agent job duration trend — growth means the publication outgrew the pattern.
  • Alert on snapshot job failure (disk, locks) and on the Distribution Agent failing to apply (perms, broken schema prerequisites).
  • Latency monitoring (tracer tokens) does not apply — "latency" is simply time since the last successful run: check MSsnapshot_history and MSdistribution_history at the distributor.

Role in other replication types

Even in transactional and merge replication, the Snapshot Agent produces the initial state. That makes its risk points (folder permissions, disk space, locks) relevant to every topology — a broken snapshot pipeline is why "reinitialize" sometimes fails as a recovery step. Alternatives for very large databases: initialize from backup (@sync_type = 'initialize with backup') or manual schema+data load with @sync_type = 'replication support only'.
