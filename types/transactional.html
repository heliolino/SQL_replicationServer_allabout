Transactional Replication

The workhorse. Committed transactions are read from the publisher's log, queued at the distributor, and replayed at each subscriber in commit order, typically within seconds. One-way by design: publisher writes, subscribers read.

Strict ordering is the contract: a single stuck command stops everything behind it for that subscription.

Why ordering is everything

The Distribution Agent applies transactions in exactly the commit order of the publisher (xact_seqno, derived from LSNs). This guarantees the subscriber is always a consistent point-in-time image of the published articles — but it also means the pipeline is head-of-line blocking: one failing command (constraint violation, missing row, timeout) halts delivery of everything behind it for that subscription. That is why most transactional incidents present as "latency growing" and resolve to "one command erroring in a loop" — find it with sp_browsereplcmds or the agent's verbose log.

Requirements & footprint

  • Every published table needs a primary key.
  • The publication database log is part of the pipeline: plan for log growth if the Log Reader stalls.
  • Continuous agents: one Log Reader per published DB, one Distribution Agent per subscription (default).
  • Works publisher → subscriber across SQL Server versions (subscriber within two versions of the publisher), to Azure SQL Database (as subscriber), and even to non-SQL Server subscribers (Oracle — deprecated path).

What a command actually looks like

USE distribution;

-- find the transaction stream for a publication's articles
SELECT TOP 20 t.xact_seqno, t.entry_time, c.command_id, a.article
FROM dbo.MSrepl_transactions t
JOIN dbo.MSrepl_commands c ON c.xact_seqno = t.xact_seqno
JOIN dbo.MSarticles a      ON a.article_id = c.article_id
ORDER BY t.entry_time DESC;

-- decode commands into readable text (the support tool for stuck commands)
EXEC sp_browsereplcmds
     @xact_seqno_start = '0x0000002B000001D8000A',
     @xact_seqno_end   = '0x0000002B000001D8000A';
-- → {CALL [sp_MSins_dboOrders] (123, N'ACME', 2026-11-15, ...)}

Latency expectations & measurement

  • Healthy steady-state latency is single-digit seconds; the floor is the sum of Log Reader polling (default 5 s), distributor write, and Distribution Agent polling/apply.
  • Measure precisely with tracer tokens, continuously with sp_replcounters (publisher side) and Replication Monitor (per-subscription).
  • Tuning levers live on the agents — see Performance & Latency.
