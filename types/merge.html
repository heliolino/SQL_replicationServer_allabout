Merge Replication

Built for everyone writes, everyone syncs eventually: field devices, branch offices, occasionally-connected laptops. Triggers track changes at every node; the Merge Agent reconciles them per sync session and resolves conflicts by rule instead of stopping.

☁ Not available on Azure SQL Managed Instance

Merge replication is not supported on MI — neither as publisher nor as subscriber. If a topology needs merge semantics in Azure, it needs SQL Server on an Azure VM; for one-way MI scenarios use transactional replication (MI setup guide) and move the multi-writer logic into the application.

download (publisher → subscriber) upload (subscriber → publisher) No distributor queue: for merge, the distribution DB stores history only.

What merge does to your schema

  • Adds a uniqueidentifier ROWGUIDCOL column (default name rowguid) with a unique index to every article that lacks one — this changes INSERT statements that don't use column lists, a classic app-breaking surprise.
  • Creates INSERT/UPDATE/DELETE triggers on every article to log changes into MSmerge_contents / MSmerge_tombstone.
  • Groups changes into generations (batches per article/partition) recorded in MSmerge_genhistory — the unit of exchange between nodes.
  • Lineage metadata per row records which node changed what — the basis of conflict detection.

Conflict detection & resolution

  1. Detect. During sync the agent compares row versions (lineage). A conflict = the same row (or column, with column-level tracking) changed at both nodes since the last sync.
  2. Resolve. The article's resolver picks a winner. Default: publisher/higher-priority node wins (subscriber priorities 0–99.9 set at subscription time). Alternatives: earliest/latest wins, additive, averaging, custom business-rule resolvers (COM or stored procedure based).
  3. Log. The losing version goes to conflict tables (MSmerge_conflicts_info + per-article conflict tables), viewable in the Conflict Viewer (SSMS → publication → View Conflicts) or via sp_helpmergearticleconflicts.
⚠ Conflicts are silent data loss unless someone reads the log

Merge never stops on a conflict — it resolves and moves on. If nobody reviews the conflict tables, losing changes simply vanish from the loser's point of view. Make conflict-table review part of the operational runbook, and design filters so two nodes rarely own the same row.

Filters: the real superpower

Merge supports parameterized row filters — each subscriber receives only its partition, evaluated per-subscriber at sync time: 

EXEC sp_addmergearticle
     @publication = N'FieldSalesPub',
     @article = N'Orders', @source_owner = N'dbo', @source_object = N'Orders',
     @subset_filterclause = N'SalesRep = HOST_NAME()';   -- each device gets its rows

-- join filter: child tables follow their parent's partition
EXEC sp_addmergefilter
     @publication = N'FieldSalesPub',
     @article = N'OrderLines',
     @filtername = N'OrderLines_Orders',
     @join_articlename = N'Orders',
     @join_filterclause = N'OrderLines.OrderID = Orders.OrderID',
     @join_unique_key = 1;

With precomputed partitions (default when possible) partition membership is evaluated ahead of sync, making per-device syncs fast. Changing a row's filter column moves it between partitions — a partition change, one of the more expensive merge operations.

Identity management

Since all nodes insert, merge manages identity columns by handing each node a range (@identity_range, @pub_identity_range) enforced by a check constraint. When a node exhausts ~80% of its range, a new one is allocated at next sync — if it can reach the publisher. See the ⚠ marker: range exhaustion while offline is a classic field-device incident (error 548).

Sync sessions & schedules

  • The Merge Agent is not continuous by default — it runs scheduled sync sessions (or on demand from the client, including via RMO / web sync).
  • Web synchronization lets internet clients sync over HTTPS through IIS — no VPN or direct SQL connectivity.
  • Exchange order: upload subscriber changes first, then download. -ExchangeType can restrict to one direction.
  • Validation: run syncs with -Validate periodically, or sp_validatemergesubscription, to catch non-convergence.

Support quick checks

-- conflict backlog
SELECT * FROM MSmerge_conflicts_info ORDER BY conflict_time DESC;

-- identity range state
SELECT * FROM MSmerge_identity_range_allocations ORDER BY time_of_allocation DESC;

-- sync history (at the distributor)
SELECT TOP 50 * FROM distribution.dbo.MSmerge_history ORDER BY time DESC;

-- metadata bloat: tombstones/contents should be cleaned by retention
EXEC sp_mergemetadataretentioncleanup;   -- normally runs automatically per retention
🛑 Merge retention (-MetadataRetentionCleanup) is unforgiving

A subscriber that doesn't sync within the publication retention period (default 14 days) is expired and must be reinitialized — and metadata cleanup makes this unrecoverable by design. For fleets of devices, track "days since last successful sync" per subscriber and alert well before the deadline.
