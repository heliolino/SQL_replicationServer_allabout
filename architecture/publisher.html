Publisher — where the data is born

The Publisher owns the source database and defines what is replicated (publications and articles) and how (filters, article options). For transactional replication its transaction log doubles as the first queue of the pipeline.

replicated log records harvested by the Log Reader

Publications and articles

A publication is the unit of subscription: a named set of articles from a single database. An article is one replicated object. For tables you control exactly what ships:

  • Row filters (static): a WHERE clause per article — only matching rows replicate. Merge replication adds parameterized filters (HOST_NAME(), SUSER_SNAME()) and join filters.
  • Column filters: exclude columns (e.g. PII) from the article. The primary key columns are always required.
  • Schema options (@schema_option bitmask): whether to script constraints, indexes, triggers, collation, etc. to the subscriber.
  • Pre-creation command (@pre_creation_cmd): what the snapshot does if the table exists at the subscriber — drop (default), delete, truncate, or none.
  • Delivery format (@ins_cmd/@upd_cmd/@del_cmd): by default changes apply through auto-generated procedures (CALL sp_MSins_dboOrders…), which is also your hook for custom conflict/soft-delete logic at the subscriber.
⚠ Every transactional article needs a primary key

Transactional replication requires a PK on every published table — replicated UPDATEs/DELETEs target rows by key. Tables without a PK simply don't appear in the article picker. Merge replication instead requires (and will add) a rowguidcol uniqueidentifier column on every article.

How the log becomes the replication queue

  1. Mark at commit. When a database is enabled for transactional publishing (sp_replicationdboption @optname='publish'), log records touching published articles are flagged "for replication". This is why log_reuse_wait_desc can report REPLICATION.
  2. Harvest. The Log Reader Agent calls sp_replcmds in a loop against the publication database. The proc walks the log from the last harvested LSN, returning only committed transactions, already translated into logical commands.
  3. Acknowledge. After writing a batch to the distribution DB, the agent calls sp_repldone to advance the "replicated up to here" watermark. Only records behind the watermark become eligible for log truncation.
🛑 sp_repldone is not a cleanup tool

Internet folklore suggests EXEC sp_repldone @xactid=NULL, @xact_seqno=NULL, @numtrans=0, @time=0, @reset=1 to "fix" a full log. It marks everything as replicated without delivering it — subscribers silently lose those transactions and usually need full reinitialization. Treat it as a last resort performed with eyes open, never a routine fix.

Publisher-side metadata worth querying

-- what is published in this database?
USE SalesDB;
EXEC sp_helppublication;          -- publications
EXEC sp_helparticle @publication = 'SalesPub';  -- articles + options
EXEC sp_helpsubscription;         -- who subscribes

-- raw catalog
SELECT * FROM dbo.syspublications;
SELECT * FROM dbo.sysarticles;
SELECT * FROM dbo.syssubscriptions;

-- pending transactions the Log Reader has not harvested yet
EXEC sp_repltrans;                -- one row per waiting transaction
DBCC OPENTRAN;                    -- shows oldest replicated (un-harvested) transaction

-- per-database log reader throughput & latency
EXEC sp_replcounters;

NOT FOR REPLICATION

Identity columns, triggers, FK and check constraints can be created NOT FOR REPLICATION: they fire/enforce for normal user DML but are skipped when a replication agent applies changes. This prevents double-firing triggers, identity reseeding by the agent, and FK failures from apply order. The snapshot scripts these automatically when @schema_option includes the relevant bits — but home-made triggers on subscriber tables are a classic cause of non-convergence when they are missing the NFR flag.

Publication security

  • Publication Access List (PAL) — logins allowed to subscribe and run agents against the publication: sp_help_publication_access, sp_grant_publication_access.
  • The Log Reader Agent connects to the publisher with a login that needs db_owner in the publication database.
  • sysadmin is required to configure publishing itself (enabling the database, creating the distributor link).
