Agents — the five workers of replication

Agents are the only moving parts: stand-alone executables run as SQL Server Agent job steps. When "replication is broken", in practice an agent is stopped, failing, or slow. Learn each agent's job, where it runs, and its failure modes.

☁ Agents on Azure SQL Managed Instance

The same five agents exist as the same msdb jobs, but they run inside the MI under Microsoft-managed accounts: create them with @job_login = NULL, @job_password = NULL and give them SQL authentication logins for the publisher/distributor/subscriber connections. There is no local file system you control, so the -Output C:\… verbose-log trick isn't available — diagnose from the history tables and MSrepl_errors instead. The Snapshot Agent writes to the Azure file share, not a local folder. Details: MI-to-MI setup.

✅ Support reflex: find the agent first

Every replication incident maps to an agent. Jobs live in msdb under categories REPL-Snapshot, REPL-LogReader, REPL-Distribution, REPL-Merge, REPL-QueueReader. Agent naming convention: <Publisher>-<PubDB>-<Publication>-<Subscriber>-<n>.

1 · Snapshot Agent (snapshot.exe)

  • Used by all types, but only for (re)initialization. Not continuous: runs when you start it or on schedule.
  • Writes article schema (.sch), data (.bcp), indexes/constraints (.idx, .dri) and pre-scripts (.pre) to the snapshot folder.
  • Transactional publications default to a concurrent snapshot (short schema locks only); snapshot publications take shared locks for the duration.
  • Start it with sp_startpublication_snapshot or by starting the REPL-Snapshot job.

2 · Log Reader Agent (logread.exe)

  • One per published database (shared by all its transactional publications). Runs continuously at the distributor.
  • Reads only committed transactions, translates them into commands, writes batches to MSrepl_commands/MSrepl_transactions, then advances the truncation watermark with sp_repldone.
  • Key tuning parameters: -ReadBatchSize, -PollingInterval, -MaxCmdsInTran (split giant transactions).
  • If it stops: latency grows and the publisher's log grows — a double incident. See ⚠ markers.

3 · Distribution Agent (distrib.exe)

  • Applies the initial snapshot, then pending commands, to each subscriber in commit order. Used by snapshot and transactional replication.
  • *By default one agent per subscription; @independent_agent = 'false' publications share one agent per publisher-DB/subscriber-DB pair.
  • Push: runs at the distributor. Pull: runs at the subscriber. Continuous (-Continuous) or scheduled.
  • Key tuning: -CommitBatchSize, -CommitBatchThreshold, -QueryTimeout, -SubscriptionStreams (parallel apply), -SkipErrors (dangerous — see common errors).

4 · Merge Agent (replmerg.exe)

upload: subscriber changes download: publisher changes
  • Per sync session: upload subscriber changes, download publisher changes, detect conflicts by comparing generation/lineage metadata, apply the resolver's winner on both sides.
  • Changes are tracked by triggers into MSmerge_contents (data) and MSmerge_tombstone (deletes) — no log reading, no distributor queue (distribution DB stores only history for merge).
  • Key tuning: -ExchangeType (upload/download only), -UploadGenerationsPerBatch, -Validate, web synchronization over HTTPS for internet clients.

5 · Queue Reader Agent (qrdrsvc.exe)

  • Serves queued updating subscriptions only (deprecated feature): applies changes made at subscribers back to the publisher from a queue.
  • One per distribution database, runs at the distributor, continuous.
  • Support stance: if you meet one in the wild, the design predates 2012 — flag for migration to merge or P2P rather than invest in tuning it.

Agent profiles — the right way to change parameters

Agent parameters can be set per job step (the -Parameter style on the command line) or via agent profiles stored at the distributor (MSagent_profiles). Profiles are the maintainable choice: they survive job recreation and apply to groups of agents. 

-- list profiles and their parameters
EXEC sp_help_agent_profile;
EXEC sp_help_agent_parameter @profile_id = 4;   -- e.g. default Distribution profile

-- create a custom profile with a bigger query timeout, then assign in
-- Replication Monitor → Agent → Profile, or with sp_update_agent_profile
EXEC sp_add_agent_profile @profile_name = N'LongTimeout',
     @agent_type = 3,               -- 1 snapshot, 2 logreader, 3 distribution, 4 merge, 9 queuereader
     @profile_type = 0;
EXEC sp_add_agent_parameter @profile_id = @@IDENTITY /* see note */,
     @parameter_name = N'-QueryTimeout', @parameter_value = N'3600';

Built-in alternates worth knowing: Verbose history (debugging), Continue on data consistency errors (the profile equivalent of -SkipErrors 2601:2627:20598 — same dangers), Slow link (merge over WAN).
