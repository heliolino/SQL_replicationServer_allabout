The three server roles

Publisher

Owns the source data. Defines publications and articles. Its transaction log is the beating heart of transactional replication.

Distributor

Hosts the distribution database — the store-and-forward queue, agent history, and cleanup jobs. Local (same server as publisher) or remote.

Subscriber

Receives data via push or pull subscriptions. Readable immediately; writable only in merge / P2P / updatable designs.

One physical server can hold several roles at once — the smallest topology is a single instance acting as Publisher + Distributor with a Subscriber database on the same machine.

The five agents — who runs where

Agents are stand-alone executables (in …\COM\ under the SQL Server installation directory) that SQL Server Agent runs as job steps. Each is a separate Windows process connecting to two or three servers. Full mechanics with per-agent animations: Replication Agents.

Where everything lives on disk and in msdb

  • Publication database — publisher-side metadata: sysarticles, syspublications, systranschemas, plus IsPublished markings in the log.
  • distribution database — commands (MSrepl_commands), transactions (MSrepl_transactions), subscriptions (MSsubscriptions), agent metadata and history (MSlogreader_history, MSdistribution_history, MSsnapshot_history, MSmerge_history), errors (MSrepl_errors).
  • msdb (on each server running agents) — the SQL Agent jobs in categories REPL-LogReader, REPL-Distribution, REPL-Snapshot, REPL-Merge, plus cleanup and monitoring jobs.
  • Snapshot folder — the UNC working directory holding generated .sch (schema), .bcp (data), .pre (pre-scripts), .idx/.dri (indexes/constraints) files.
  • Subscription database — the delivered tables plus the auto-generated apply procedures (sp_MSins_*, sp_MSupd_*, sp_MSdel_*) and, for transactional, MSreplication_subscriptions.

Support-engineer mental model

✅ The one-sentence model

Transactional replication is a pipeline of three queues: the publisher's transaction log (drained by the Log Reader), the distribution database (drained by Distribution Agents), and the batch the agent is currently applying at the subscriber (drained by the subscriber's ability to commit). Every latency incident is one of these three queues backing up — your first job is to find which one.
