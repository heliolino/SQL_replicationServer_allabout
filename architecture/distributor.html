Distributor — the store-and-forward heart

The Distributor hosts the distribution database: the queue between publishers and subscribers, the agents' home base, their history, and the cleanup machinery. When replication breaks, this is where the evidence lives — and where most of the disk-space incidents happen.

☁ The distributor can be an Azure SQL Managed Instance

Everything on this page — the distribution DB, queue tables, history, retention and cleanup jobs — works the same when the distributor is an MI. The one structural difference: the snapshot working directory is not a local disk or file-server share but an Azure file share in a storage account, registered with the storage key via sp_adddistpublisher. Disk-space incidents on an MI distributor count against the instance's storage allocation. Setup: MI-to-MI walkthrough.

Retention — the two clocks

Two independent retention settings govern the distributor, and confusing them causes incidents:

  1. Distribution (transaction) retention — @min_distretention (default 0 h) / @max_distretention (default 72 h): how long delivered commands stay in MSrepl_commands before cleanup deletes them. Commands not yet delivered to some subscriber are kept regardless — until the second clock fires.
  2. Publication (subscription) retention — @retention on the publication (default 336 h = 14 days): how long a subscription may remain un-synchronized before it is deactivated/expired. Once expired, cleanup removes its commands and the subscription must be reinitialized.
-- current retention settings
EXEC sp_helpdistributiondb;                 -- min/max distribution retention, history retention
EXEC sp_helppublication @publication = 'SalesPub';  -- retention column (hours)

-- how deep is the queue?
USE distribution;
SELECT COUNT(*) AS pending_commands FROM dbo.MSrepl_commands WITH (NOLOCK);

-- undistributed commands per subscription (what Replication Monitor shows)
EXEC sp_replmonitorsubscriptionpendingcmds
     @publisher = 'PUB01', @publisher_db = 'SalesDB',
     @publication = 'SalesPub', @subscriber = 'SUB01',
     @subscriber_db = 'SalesReporting', @subscription_type = 0;  -- 0 = push

⚠ Disabled cleanup = time bomb

Teams sometimes disable "Distribution clean up" during an incident because it blocks agents — and forget it. The distribution DB then grows until the disk fills, taking down every publication through this distributor. If you find cleanup disabled, treat it as an active incident: find out why, fix the root cause, re-enable, and let it drain off-hours.

Backing up the distributor

  • The distribution database should be in simple recovery in most topologies and backed up regularly — losing it means rebuilding every publication.
  • With sync with backup enabled on publication + distribution DBs, the Log Reader will not hand out transactions that are not yet backed up at the publisher, guaranteeing restore-consistency at the cost of latency.
  • For HA, cluster the distributor instance or (SQL 2017 CU6+) place the distribution database in an Availability Group — check version-specific support before recommending.
