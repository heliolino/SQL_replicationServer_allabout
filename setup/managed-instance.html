Transactional replication between SQL Managed Instances — initialized from backup, not snapshot

Three Azure SQL Managed Instances: a publisher MI, a dedicated distributor MI, and a subscriber MI — with the subscriber initialized by backup & restore instead of a snapshot. On MI this has a twist that shapes the whole procedure: Microsoft owns the backup chain. Automated backups run when Azure decides, you cannot schedule or trigger them, and you never see the backup files. The initialization below is built around that fact.

initialization path: the subscriber DB is born from Azure's own automated backups via point-in-time restore
⚠ The MI backup twist — read this before choosing a route

On a Managed Instance, Microsoft's service takes all backups automatically; you cannot schedule, trigger, or access them. The only backup a user may take is COPY_ONLY ... TO URL — and even that is blocked when the database uses service-managed TDE (the default). The classic @sync_type = 'initialize with backup' needs to read the backup media, which it can never do against Azure's hidden backup chain. That leaves two backup/restore routes:

RouteHowWorks whenSync type
A — PITR + LSN (recommended) Point-in-time restore of the publisher DB from Azure's automated backups directly onto the subscriber MI, then start delivery from a known LSN Always — including service-managed TDE; uses exactly the backups Microsoft already takes initialize from lsn
B — COPY_ONLY to URL User-taken COPY_ONLY backup to Azure Blob, restore from URL on the subscriber, point the subscription at the backup file Only when the DB is not under service-managed TDE (TDE off, or customer-managed key available on both instances) initialize with backup, @backupdevicetype = 'URL'

Step 0 — prerequisites & networking

  • Three Managed Instances in the same VNet, or peered VNets. NSG rules must allow TCP 1433 and the redirect range 11000–11999 between the MI subnets, and outbound 445 to Azure Files (a blocked 445 surfaces later as OS error 53 on the share).
  • SQL Authentication between all replication participants — create the same strong-password login (e.g. TRANREPLADMIN) on all three instances.
  • An Azure storage account with: a file share (the replication working directory — required for the distributor even when you never plan to use snapshots) and, for Route B, a blob container for the backup file.
  • Distributor MI service tier/version equal to or higher than the publisher.
  • Push subscriptions only in mixed topologies; MI → MI works as push and that is what this page uses — the Distribution Agent runs at the distributor, close to the queue.
  • For Route A: Azure PowerShell (Az.Sql) and permission to run a point-in-time restore in the subscription.

Step 1 — configure the dedicated distributor MI

Run on dist-mi. Same procs as on-box SQL Server (full walkthrough: Configure Distributor), plus the two MI-specific arguments: the Azure file share as working directory and the storage key.

USE master;
EXEC sp_adddistributor
     @distributor = N'dist-mi.abc123xyz.database.windows.net',  -- its own FQDN
     @password    = N'<distributor_admin_link_password>';

EXEC sp_adddistributiondb
     @database = N'distribution',
     @security_mode = 0,
     @login = N'TRANREPLADMIN', @password = N'<strong password>';

EXEC sp_adddistpublisher
     @publisher        = N'pub-mi.abc123xyz.database.windows.net',   -- the PUBLISHER MI
     @distribution_db  = N'distribution',
     @security_mode    = 0,
     @login = N'TRANREPLADMIN', @password = N'<strong password>',
     @working_directory = N'\\replstorage.file.core.windows.net\replshare',
     @storage_connection_string =
       N'DefaultEndpointsProtocol=https;AccountName=replstorage;AccountKey=<storage account key>';
⚠ Backslashes only in the working directory

\\account.file.core.windows.net\share — forward slashes in this path cause connection errors that look like networking failures. And yes, the working directory is required even for backup initialization: the distributor infrastructure and any later re-snapshot depend on it.

Step 2 — point the publisher MI at the remote distributor

USE master;
EXEC sp_adddistributor
     @distributor = N'dist-mi.abc123xyz.database.windows.net',
     @password    = N'<distributor_admin_link_password>';   -- MUST match step 1

Verify the link before continuing: EXEC sp_get_distributor; at the publisher must show installed = 1 and the distributor FQDN.

Step 3 — create the publication with the backup-init flags

Still on pub-mi. Two publication properties are what make backup initialization possible at all: allow_initialize_from_backup marks a start LSN in the log, and immediate_sync keeps delivered commands in the distribution DB for the whole retention window so a subscriber created later can still catch up from its restore point.

EXEC sp_replicationdboption @dbname = N'SalesDB', @optname = N'publish', @value = N'true';

USE SalesDB;
EXEC sp_addlogreader_agent
     @job_login = NULL, @job_password = NULL,        -- MI runs agents under managed accounts
     @publisher_security_mode = 0,
     @publisher_login = N'TRANREPLADMIN', @publisher_password = N'<strong password>';

EXEC sp_addpublication
     @publication = N'MIPub',
     @description = N'MI-to-MI transactional, initialized from backup',
     @repl_freq   = N'continuous',
     @independent_agent = N'true',
     @immediate_sync    = N'true',                   -- required for backup/LSN init
     @allow_initialize_from_backup = N'true',        -- required: marks the init LSN
     @sync_method = N'native',
     @allow_push  = N'true', @allow_pull = N'false',
     @replicate_ddl = 1, @retention = 0;

EXEC sp_addarticle @publication = N'MIPub', @article = N'Orders',
     @source_owner = N'dbo', @source_object = N'Orders',
     @type = N'logbased', @identityrangemanagementoption = N'manual';
-- repeat sp_addarticle per table

EXEC sp_grant_publication_access @publication = N'MIPub', @login = N'TRANREPLADMIN';
✅ Publication already exists? Flip the flags, then refresh the LSNs
EXEC sp_changepublication @publication = N'MIPub',
     @property = N'allow_initialize_from_backup', @value = N'true';
EXEC sp_changepublication @publication = N'MIPub',
     @property = N'immediate_sync', @value = N'true';
-- then run the Snapshot Agent ONCE so the internal LSN markers
-- (min_autonosync_lsn) are refreshed — no subscriber consumes this snapshot

Step 4 — Route A: initialize from Azure's automated backups (PITR + initialize from lsn)

This is the route that embraces the MI reality: you can't take the backup, but Azure already did — a point-in-time restore materializes the publisher DB on the subscriber MI at any second you choose. The craft is picking a restore time that maps to a known LSN, then telling the subscription to deliver everything after that LSN.

  1. Quiesce if you can. Pausing application writes on the published tables for 15–30 minutes around the chosen point makes the LSN↔time mapping unambiguous and removes every edge case in step 3.
  2. Read the publication's init LSN at the publisher: 
    SELECT name, allow_initialize_from_backup, immediate_sync, min_autonosync_lsn
FROM dbo.syspublications;
-- both flags must be 1; min_autonosync_lsn (e.g. 0x000000A0000009F8003E)
-- is the safe starting LSN — note it down
  3. Map that LSN to a wall-clock time at the distributor — this becomes your PITR timestamp: 
    USE distribution;
SELECT TOP 50 xact_seqno, entry_time        -- entry_time is UTC
FROM dbo.MSrepl_transactions
WHERE publisher_database_id =
      (SELECT id FROM dbo.MSpublisher_databases WHERE publisher_db = N'SalesDB')
ORDER BY xact_seqno;
-- find the transactions bracketing your min_autonosync_lsn and pick a
-- point-in-time BETWEEN them (a quiesced gap makes this trivial)
  4. Point-in-time restore the publisher DB onto the subscriber MI. PowerShell, because the portal rounds the seconds you need: 
    Connect-AzAccount
Set-AzContext -SubscriptionId "<subscription-id>"

Restore-AzSqlInstanceDatabase -FromPointInTimeBackup `
  -ResourceGroupName   "rg-replication" `
  -InstanceName        "pub-mi" `
  -Name                "SalesDB" `
  -PointInTime         "2026-11-16T13:16:54Z" `      # UTC, between the bracketing txns
  -TargetResourceGroupName    "rg-replication" `
  -TargetInstanceName         "sub-mi" `
  -TargetInstanceDatabaseName "SalesDB"
    The restore brings the whole database — including tables that aren't articles. Fine for a full-database publication; if you publish 3 tables out of 3,000, a snapshot might honestly be cheaper.
  5. Fix security on the restored DB (sub-mi): create/repair the TRANREPLADMIN login, map it into SalesDB, add to db_owner — the Distribution Agent connects as it.
  6. Create the subscription from the LSN — no backup device, just the coordinate: 
    EXEC sp_addsubscription
     @publication       = N'MIPub',
     @subscriber        = N'sub-mi.abc123xyz.database.windows.net',
     @destination_db    = N'SalesDB',
     @subscription_type = N'Push',
     @article           = N'all',
     @update_mode       = N'read only',
     @subscriber_type   = 0,
     @sync_type         = N'initialize from lsn',
     @subscriptionlsn   = 0x000000A0000009F8003E;   -- binary literal, NO quotes

EXEC sp_addpushsubscription_agent
     @publication   = N'MIPub',
     @subscriber    = N'sub-mi.abc123xyz.database.windows.net',
     @subscriber_db = N'SalesDB',
     @subscriber_security_mode = 0,
     @subscriber_login = N'TRANREPLADMIN', @subscriber_password = N'<strong password>',
     @job_login = NULL, @job_password = NULL,
     @frequency_type = 64;                           -- run continuously
  7. Verify, then un-quiesce. Replication Monitor (or the health check sweep) should show the agent delivering; post a tracer token and compare row counts.
🛑 Picked the wrong LSN or time?

The symptoms are immediate and recognizable: 20598 (row not found) if the restore point is ahead of your LSN (commands replay against rows that already changed), or 2601/2627 duplicates if it is behind (inserts re-applied). Decode what the agent is trying to apply with sp_browsereplcmds (coordinates explained in the LSN deep dive), drop the subscription, adjust @subscriptionlsn or the PITR time, and repeat — the restore is cheap to redo.

Step 4 — Route B: user-taken COPY_ONLY backup to URL (when TDE allows)

If the database is not protected by service-managed TDE (TDE disabled, or customer-managed key present on both instances), you can take the one kind of backup MI permits and use the classic mechanism. The backup must be taken after step 3's flags are enabled.

-- ① on BOTH instances (master): credential named exactly as the container URL
CREATE CREDENTIAL [https://replstorage.blob.core.windows.net/backups]
WITH IDENTITY = 'SHARED ACCESS SIGNATURE',
     SECRET   = '<SAS token without leading ?>';

-- ② PUBLISHER MI — COPY_ONLY is the only full backup MI allows you
BACKUP DATABASE SalesDB
TO URL = N'https://replstorage.blob.core.windows.net/backups/SalesDB_init.bak'
WITH COPY_ONLY, COMPRESSION, INIT;

-- ③ SUBSCRIBER MI
RESTORE DATABASE SalesDB
FROM URL = N'https://replstorage.blob.core.windows.net/backups/SalesDB_init.bak';
EXEC sp_addsubscription
     @publication       = N'MIPub',
     @subscriber        = N'sub-mi.abc123xyz.database.windows.net',
     @destination_db    = N'SalesDB',
     @subscription_type = N'Push',
     @article           = N'all',
     @update_mode       = N'read only',
     @subscriber_type   = 0,
     @sync_type         = N'initialize with backup',
     @backupdevicetype  = N'URL',
     @backupdevicename  = N'https://replstorage.blob.core.windows.net/backups/SalesDB_init.bak';
-- the LSN is read from the backup header: every transaction committed AFTER
-- the backup is delivered automatically — no quiesce required
-- then sp_addpushsubscription_agent exactly as in Route A
⚠ Route B fails on service-managed TDE — by design

BACKUP ... WITH COPY_ONLY is refused for databases encrypted with a service-managed key (the key can't leave Azure's control, so the backup would be unrestorable anyway). That is precisely why Route A exists: the PITR path never needs the backup file in your hands. Don't disable TDE just to use Route B.

Verification checklist

  • ☐ sp_replcounters on pub-mi: latency seconds, not hours; pending count draining
  • ☐ Agent state sweep on dist-mi: Log Reader + Distribution Agent "In progress/Idle" (health check, check 1)
  • ☐ Tracer token completes end-to-end (how)
  • ☐ Row counts match per article (health check, check 4)
  • ☐ A test INSERT at pub-mi arrives at sub-mi within the SLA
  • ☐ NSG review: 1433 + 11000–11999 between MI subnets, 445 outbound to storage still green after any network change
