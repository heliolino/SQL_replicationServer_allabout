Step 2 — Create the Publication

Defines what replicates. Affects: Publisher (enables the DB for publishing, creates publication + articles, starts marking the log) and Agents (creates the Log Reader and Snapshot Agent jobs).

Option A — SSMS wizard (New Publication)

  1. Connect to the publisher → Replication → Local Publications → right-click → New Publication…
  2. Publication Database: pick the source DB. The wizard silently runs sp_replicationdboption 'publish' on finish — from that moment the log starts retaining replicated records.
  3. Publication Type: Snapshot / Transactional / (Transactional with updatable — deprecated) / Merge / Peer-to-Peer. This choice is permanent per publication.
  4. Articles: tick tables (PK-less tables are greyed out for transactional), procs, views. Per-article Article Properties → set @pre_creation_cmd, copy indexes/triggers options, destination name/schema overrides.
  5. Filter Table Rows: add static row filters (transactional) or parameterized/join filters (merge).
  6. Snapshot Agent page: "Create a snapshot immediately" and/or schedule. For big tables at busy hours, untick "immediately" and run it off-hours instead.
  7. Agent Security: set the Snapshot Agent and Log Reader Agent accounts (see prerequisites §3). Avoid "Run under the SQL Server Agent service account" in production.
  8. Finish with a name — and generate the script for source control.

Option B — pure T-SQL (transactional example)

USE master;
-- 1. enable the database for transactional publishing (idempotent)
EXEC sp_replicationdboption @dbname = N'SalesDB', @optname = N'publish', @value = N'true';
-- merge would be: @optname = N'merge publish'

USE SalesDB;
-- 2. the Log Reader Agent job for this DB (wizard does this implicitly)
EXEC sp_addlogreader_agent
     @job_login = N'DOMAIN\replLogReader', @job_password = N'***',
     @publisher_security_mode = 1;     -- Windows auth back to the publisher

-- 3. the publication
EXEC sp_addpublication
     @publication = N'SalesPub',
     @publication_type   = N'transactional',  -- implied by repl_freq below in older scripts
     @repl_freq          = N'continuous',
     @sync_method        = N'concurrent',     -- concurrent snapshot: minimal locks
     @retention          = 336,               -- subscription expiry (hours)
     @allow_push = N'true', @allow_pull = N'true',
     @independent_agent  = N'true',
     @immediate_sync     = N'false',          -- see note below!
     @status             = N'active';

-- 4. its snapshot agent job
EXEC sp_addpublication_snapshot
     @publication = N'SalesPub',
     @job_login = N'DOMAIN\replSnapshot', @job_password = N'***',
     @publisher_security_mode = 1;

-- 5. articles
EXEC sp_addarticle
     @publication = N'SalesPub',
     @article = N'Orders',
     @source_owner = N'dbo', @source_object = N'Orders',
     @type = N'logbased',
     @pre_creation_cmd = N'drop',
     @schema_option = 0x000000000803509F,     -- common default: PK, indexes, defaults...
     @ins_cmd = N'CALL sp_MSins_dboOrders',
     @upd_cmd = N'SCALL sp_MSupd_dboOrders',
     @del_cmd = N'CALL sp_MSdel_dboOrders';

-- optional row filter
EXEC sp_articlefilter
     @publication = N'SalesPub', @article = N'Orders',
     @filter_name = N'FLT_Orders_EU',
     @filter_clause = N'Region = N''EU''';
EXEC sp_articleview
     @publication = N'SalesPub', @article = N'Orders',
     @view_name = N'VW_Orders_EU',
     @filter_clause = N'Region = N''EU''';
⚠ @immediate_sync — small flag, big consequences

@immediate_sync = 'true' (the wizard's default!) keeps a full snapshot and all commands for the entire retention period so that new subscribers can join without a fresh snapshot. That convenience makes the distribution database retain commands for 336 hours instead of until-delivered — the single most common cause of "why is my distribution DB huge?". For most topologies set it (and @allow_anonymous) to 'false' and generate snapshots on demand when subscribers join.

Verify

EXEC sp_helppublication @publication = N'SalesPub';
EXEC sp_helparticle    @publication = N'SalesPub';

-- jobs created (at the distributor for push topology)
SELECT j.name, c.name AS category
FROM msdb.dbo.sysjobs j JOIN msdb.dbo.syscategories c ON c.category_id = j.category_id
WHERE c.name IN ('REPL-LogReader','REPL-Snapshot');

-- log reader connected and scanning?
EXEC sp_replcounters;   -- returns a row per published DB once the log reader has run

Generating the first snapshot

EXEC sp_startpublication_snapshot @publication = N'SalesPub';
-- watch it:
SELECT TOP 5 * FROM distribution.dbo.MSsnapshot_history ORDER BY time DESC;
  • Watch duration and the snapshot folder filling with a dated subfolder per run.
  • Concurrent snapshots (transactional default) only hold schema locks briefly at start/end — but the BCP reads still cost IO; prefer off-hours for the first big one.

Publication-level settings worth knowing later

Setting (sp_changepublication)Why support touches it
retentionLengthen before planned subscriber outages to avoid expiry/reinit
allow_initialize_from_backupEnables no-snapshot initialization for very large DBs
replicate_ddl1 = ALTERs flow to subscribers (default); 0 = schema frozen
allow_anonymous / immediate_syncThe distribution-DB-bloat pair — see callout above
status (active/inactive)Inactive publications accept no new subscriptions
