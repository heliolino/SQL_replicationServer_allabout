Prerequisites & planning checklist

Most replication installs that go wrong, go wrong before the first wizard page: a missing feature, a service account without share access, a @@SERVERNAME mismatch. Work through this page first.

1 · Feature & edition requirements

CheckDetails
Replication components installed"SQL Server Replication" feature must be selected in setup on publisher, distributor, and subscriber instances. Verify: SELECT SERVERPROPERTY('IsFullTextInstalled') is irrelevant — check sys.fn_installed_features or re-run setup → Installed features.
EditionExpress can only be a subscriber (pull). Web edition: subscriber only. P2P requires Enterprise on all peers. Everything else works on Standard.
Version mixDistributor version ≥ publisher version; subscriber within two versions of the publisher (transactional). Merge: subscriber ≤ publisher version.
SQL Server AgentRunning and set to Automatic start on every box that hosts agents. Replication is dead in the water without it.
AzureAzure SQL DB: subscriber only (push, transactional/snapshot). Azure SQL MI: publisher/distributor/subscriber supported. Document which before promising anything.

2 · Server naming — the classic trap

Replication refuses IPs and aliases for topology links; it wants the real instance names, consistent everywhere.

-- these two must match on every instance involved:
SELECT @@SERVERNAME        AS server_name_variable,
       SERVERPROPERTY('ServerName') AS serverproperty_name;

-- if they differ (renamed machine, cloned VM):
EXEC sp_dropserver 'OLDNAME';
EXEC sp_addserver  'NEWNAME', 'local';
-- then restart the SQL Server service and re-check
  • All connections between replication servers use the instance name (e.g. PUB01\SQL2022). DNS must resolve it from every box; firewalls must allow 1433/instance port both ways.
  • Named instances need the SQL Browser service or fixed ports + explicit server\instance,port client aliases.

3 · Service & agent accounts

Plan accounts before the wizards ask. Least-privilege per Microsoft guidance:

AgentProcess account needsConnection needs
Snapshot AgentWindows account; write on snapshot sharedb_owner in distribution DB; db_owner in publication DB
Log Reader AgentWindows accountdb_owner in distribution DB; db_owner in publication DB
Distribution Agent (push)Windows account; read on snapshot sharedb_owner in distribution DB; db_owner in subscription DB; PAL membership
Distribution Agent (pull)Account at the subscriber; read on snapshot sharePAL membership at publisher; db_owner in subscription DB
Merge AgentAs distribution agent (push/pull)PAL; db_owner both ends
⚠ Don't run agents as the SQL Server service account "because it works"

It usually works because that account is over-privileged. Then someone hardens the service account or rotates it, and replication breaks everywhere at once (see risk Agent security / login failures). One dedicated domain account per agent type, documented, with passwords in a vault, is the supportable pattern.

4 · The snapshot share

  1. Create a folder on the distributor with room for a full copy of your largest publication (e.g. D:\ReplData).
  2. Share it as e.g. \\DIST01\ReplData. Share + NTFS permissions: Snapshot Agent account = Change/Modify; Distribution & Merge agent accounts = Read.
  3. Always configure replication with the UNC path, never the local path — local paths break the moment you add a pull subscriber (⚠ Snapshot folder permissions risk).

5 · Database-level prerequisites

  • Transactional: every article table has a primary key. Find offenders: 
    SELECT s.name AS schema_name, t.name AS table_name
FROM sys.tables t
JOIN sys.schemas s ON s.schema_id = t.schema_id
WHERE t.is_ms_shipped = 0
  AND NOT EXISTS (SELECT 1 FROM sys.key_constraints k
                  WHERE k.parent_object_id = t.object_id AND k.type = 'PK');
  • Merge: check for apps using INSERT without column lists (rowguid column will break them) and for existing uniqueidentifier columns you may want to designate as the rowguid.
  • Recovery model: any model works for transactional replication (the log keeps replicated records regardless), but FULL is recommended on publication DBs so you keep point-in-time restore.
  • Datatypes: FILESTREAM, sparse columns, and some CLR types have restrictions — review article datatype limits before promising a table can replicate.

6 · Capacity planning quick numbers

ItemRule of thumb
Distribution DB sizeSteady state: (commands/hour × retention hours) × ~1 KB. Size for your longest tolerated subscriber outage, not the average.
Distribution DB filesPre-size data + log; autogrowth events during catch-up storms hurt. Put it on fast storage — every transaction is written here too.
Snapshot folder≥ sum of published table data sizes (BCP format ≈ data size), × 2 if snapshots can overlap.
Publisher logAdd headroom for the longest expected Log Reader outage: log holds everything un-harvested.
NetworkChange volume × command overhead must fit the link to each subscriber — especially for geo subscribers; consider pull + scheduled sync over slow links.

7 · Pre-flight checklist

  • ☐ Replication feature installed on all instances
  • ☐ SQL Server Agent auto-start everywhere
  • ☐ @@SERVERNAME correct on all instances; DNS + firewall verified both directions
  • ☐ Agent accounts created, documented, share permissions set
  • ☐ Snapshot share created and reachable from subscriber(s)
  • ☐ PKs on all transactional articles / rowguid impact assessed for merge
  • ☐ Distribution DB placement & sizing agreed; retention values chosen consciously
  • ☐ Backup plan updated: distribution DB + msdb (jobs) + publication DB are now a coordinated set
